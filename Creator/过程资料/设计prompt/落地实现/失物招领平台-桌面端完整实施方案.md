## 二、路线裁决：壳用 ZCode 式，交付用 dsh 式

两个参考产品对应两条路线，结合本项目"后端与用户同机（课程演示）+ 已有 Electron 壳"的现状，裁决如下：

| 维度 | dsh 路线（本地 Web 服务器） | ZCode 路线（Electron 壳） | 我们的取舍 |
|---|---|---|---|
| 容器 | 本地起服务，浏览器访问 | Electron 窗口 | **ZCode 壳**（已建成；答辩观感是"桌面软件"） |
| 后端位置 | 与 UI 同机（localhost） | 云端/远程 | **同机 localhost**（Spring Boot + MySQL 本就跑在演示机） |
| 文件在哪 | 生成即在用户磁盘 →"下载=原生打开" | 文件在云端 → 必须网络下载 | **dsh 语义成立**：后端在本机，交付文件天然就在用户磁盘上 |
| 认证 | 单点围栏（token→签名 cookie） | JWT Bearer | **沿用 JWT**（已有拦截器+越权测试），不引入 cookie 围栏 |
| 自更新 | 无 | electron-updater + blockmap | **明确不做**（课程体量，答辩口径"了解工业级方案，评估后不引入"） |

**核心洞察（本方案的灵魂）**：dsh 的"文件交付"之所以优雅，是因为**文件生成那一刻就在用户磁盘上**。我们的桌面端恰好满足这个前提——后端与壳同机。因此：

- **桌面端**：交付卡片点击 = 原生打开/在文件夹中显示（`shell.openPath` / `shell.showItemInFolder`），零网络传输；
- **Web 端**：同一套 delivery 记录，卡片点击 = 受控 HTTP 下载（`/api/file/download`，响应头三件套）。

一套后端能力，两种端各自选最合理的"拿文件"方式——这就是"结合两个项目"的正确姿势。

## 三、目标架构

```
┌─ 桌面端 ShiGuang.exe（Electron 壳，纯容器，已建）──────────────┐
│  main.cjs：窗口 / 探活拉起后端 / 单实例 / 深链接 / 外链守卫      │
│  P2 新增：托盘（关窗驻留）/ 窗口状态记忆 / 原生打开代理 IPC      │
│  renderer：Vue 前端（file:// hash 路由，已适配）                 │
└──────────────┬──────────────────────────────────────┘
               │ http://localhost:8080（JWT Bearer）
┌─ Spring Boot 后端 ──────────────────────────────────────────┐
│ 既有：M1~M6 业务 + E 批 + /admin/export/items.csv             │
│ P1 新增（dsh 三层解耦转译）：                                  │
│  ① 业务代码只"声明"：认领通过/搜图完成 → FileDeliveryService   │
│  ② delivery 表（持久交付事件：谁/什么文件/什么业务/状态）       │
│  ③ 受控下载 GET /api/file/download?id=（不收路径，只收 id）     │
│  ④ 桌面联动 POST /api/file/open?id=（服务端返回绝对路径，       │
│     由壳经 IPC 原生打开——路径服务端读回，浏览器永不过路径）      │
└──────────────┬──────────────────────────────────────┘
               │ 落盘
        uploads/deliveries/yyyy/MM/uuid.pdf  ← 文件生成即在用户磁盘（dsh 语义）
```

安全红线（逐条来自 dsh 踩坑记录，验收逐条证伪）：

1. 浏览器/渲染层**永远不传路径**，只传 deliveryId；路径由服务端按记录读回
2. `resolve().startsWith(root)` 防符号链接/穿越；非普通文件拒绝
3. 响应头三件套：`Cache-Control: private, no-store` + `X-Content-Type-Options: nosniff` + `Content-Disposition: attachment; filename*=UTF-8''`
4. MIME 白名单窄化：pdf/csv/zip 三类，其余拒绝
5. 越权即 403：`delivery.user_id == 当前用户`（管理员豁免）；失效 404
6. 字节上限 413；错误码与 HTTP 状态一致（沿用 B-06 口径）
7. 认证前置：下载路由在 JwtInterceptor 围栏内，各生成器不重复造认证

## 四、分阶段实施计划

### P0 · 收敛整理（半天，成员A）

按 §1.2 清单执行；`desktop/main.cjs` 的 `output` 目录改回 `release`；运行说明按"总纲引用"瘦身。
**验收**：`release/` 唯一；`grep -rn "release2" desktop/` 无输出；文档交叉引用无断链。

### P1 · 文件交付最小闭环（2~3 天，成员C 后端 + 成员D 前端）

按《文件交付能力落地流程》§2~§4 执行，裁剪如下：

1. **delivery 表**（成员E，半天）：按落地流程文档 §2 建表；本机库 ALTER + schema.sql 同步；Creator/交付文档/06 数据字典补录；**纳入 test_api 七表→八表基线**（delivery 与业务数据同走幂等，测试启事的交付物随级联清理——deleteItem 时按 biz_id 清理 delivery 行，对齐 B-05 风格）。
2. **FileDeliveryService + 受控下载**（成员C，1 天）：按落地流程 §3.1/3.2 逐条实现（校验存在/普通文件/resolve 在 deliveries 根内/越权/三件套响应头/MIME 白名单/413）。
3. **两个生成器**（成员C，1 天）：
   - `CLAIM_CERT` 认领证明 PDF：`ClaimService.audit` 通过分支生成（OpenPDF，模板填物品/双方/时间戳），交付给失主与认领人各一条 delivery；
   - `REPORT_CSV` 统计报表：把 E-08B 的 CSV 写入 deliveries 目录改走 delivery 体系（管理端卡片下载，替代独立端点）。
   - `MATCH_REPORT` 匹配报告 PDF（P2 顺手做）：以图搜图 Top-N + 汉明距离 + 缩略图，绑定核心亮点 M3。
   - 照片 zip 暂缓（价值最低，留作扩展）。
4. **前端 DeliveryCard**（成员D，1 天）：消息中心与认领详情挂卡片（标题/类型图标/大小/时间）；**动作分端**——桌面端（`window.shiguangDesktop` 存在）调 P2 的原生打开，Web 端走 fetch→blob 下载；生成中态：同步生成（课程数据量）不轮询，超 500ms 显示 loading。
5. **测试**（成员E）：单测（FileDeliveryService 越权 403/穿越 403/超限 413/失效 404）+ test_api 断言（认领通过 → delivery+1 且可下载 → 下载内容字节一致 → 删除启事后卡片 404，**先造缺口再验证**）。
6. **文档**（成员B）：Creator/交付文档/04 补 3 个端点；Creator/交付文档/01 FR5/FR6 补"认领证明/报表可交付下载"；Creator/交付文档/02 状态图补"已认领 → 证明可下载"支路；Creator/交付文档/12 补 deliveries 目录备份说明。

**验收（全部证伪式）**：修改 deliveryId 为别人的 → 403；构造 `../` 或符号链接 → 403 不泄露服务器路径；伪造 Content-Type 的 HTML → nosniff 不执行；未登录 → 401；跑完 test_api delivery 行数回基线；认领一单 → 失主消息中心出现"认领证明"卡片 → 桌面端点击用系统 PDF 阅读器打开。

### P2 · 桌面联动增强（1~2 天，成员D + 成员A）

ZCode 文档落地清单的裁剪版（壳侧）：

1. **原生打开代理**：`main.cjs` 加 `ipcMain.handle('shiguang:open-file', p => shell.openPath(p))` 与 `showItemInFolder`；preload 白名单暴露。**安全约束**：仅接受 `cfg.apiBase` 同源 `/api/file/open` 返回的、且位于 uploads 根内的路径；壳再做一次 `realpath` 前缀校验（双保险，壳不信任渲染层）。
2. **托盘驻留（可选）**：关闭窗口 → 隐藏到托盘，菜单"退出"真退出；演示机防误关。
3. **窗口状态记忆**：位置/尺寸持久化到 `userData/window-state.json`（自写 20 行，不引依赖）。
4. **匹配报告 PDF**：搜图结果页加"生成匹配报告"，桌面端直接原生打开（答辩一页纸素材）。
5. **不做**（维持既有裁决）：自更新/多窗口/推送/插件沙箱。

**验收**：断网重启壳 → 窗口位置记忆生效；点交付卡片 → PDF 用系统默认阅读器打开、"在文件夹中显示"定位到文件；托盘退出后进程列表无残留（含自动拉起的 jar）。

### P3 · 分发与答辩打磨（半天，成员A）

1. 版本号进 `package.json`（1.0.0 → 每次答辩前 +0.0.1）；安装包命名带版本（已满足）。
2. 安装指引图文（截图：下载→安装→首次启动探活弹窗→主界面）放 `Creator/交付文档/12` 新节。
3. 答辩话术（三句话）：①"桌面壳参考 ZCode Desktop 的分发与进程模型，单实例锁与深链接一键唤起"；②"文件交付参考 DeepSeek Harness 的三层解耦——业务只声明、持久事件、UI 读表渲染，下载即原生打开，因为文件生成时就在本机"；③"自更新等工业级能力评估后明确不引入，避免过度工程"。

## 六、明确不做（防范围膨胀，答辩口径统一）

| 项 | 理由 |
|---|---|
| electron-updater 自更新/差量 blockmap | 需维护更新服务器；覆盖安装即可，话术见 P3 |
| 托盘消息推送/系统通知 | 站内消息 + 30s 轮询已达标（Creator/交付文档/10 展望口径） |
| 多窗口/插件沙箱/utilityProcess | 单页应用无此需求；壳保持薄 |
| Android/iOS 双端 | 见《…Android与iOS双端落地Prompt.md》，独立排期（P1 APK 建议在文件交付之后做，APK 分发可复用 delivery 思路） |
| 照片 zip 打包下载 | 四个生成器里价值最低，留作扩展作业 |

## 七、一条主线记住本方案

> **壳学 ZCode（怎么装到桌面、怎么常驻、怎么被唤起），交付学 dsh（业务只声明 → 持久事件 → UI 读表渲染 → 桌面原生打开/Web 受控下载）。**
> 桌面端不是"浏览器套皮"，而是因为**后端就在用户机器上**，才让"生成即可打开"成立——这句话就是答辩时把两个参考产品串起来的那根线。
