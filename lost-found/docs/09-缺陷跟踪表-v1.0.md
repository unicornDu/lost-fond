# 缺陷跟踪表 v1.0

> 交付物编号 09（成员E）。严重级：P0 致命/阻断主线，P1 严重，P2 一般。
> 全部缺陷均为本项目开发/测试过程中**真实发现并已修复回归**——每条都能在代码与提交历史中对应，是答辩讲"质量保障过程"的最好素材。

| # | 标题 | 严重级 | 现象 | 根因分析 | 修复方案 | 状态 |
|---|---|---|---|---|---|---|
| 1 | 汉明距离误用逻辑异或，搜图全 100% | **P0** | 以图搜图所有结果相似度恒 100%，完全不判别 | MySQL 中 `XOR` 是**逻辑**异或（真真得假，只返回 0/1），`BIT_COUNT(XOR)` 恒 0/1，距离全 0 | `ItemImageMapper.searchByHash` 改用按位异或 `^`：`MIN(BIT_COUNT(phash ^ #{q}))` | 已修复+回归 |
| 2 | 发布图片 pHash 未入库，新启事搜不到 | **P0** | 刚发布的启事（含图）以图搜图检索不到 | `publish()` 先 `transferTo` 落盘消费了 multipart 流，随后 `getBytes()` 失败 → phash=null 静默跳过 | 改为"读一次字节，既写盘又算哈希"；并加 `POST /api/search/reindex` 兜底补算 | 已修复+回归 |
| 3 | 搜图 Top-N 被待审核项挤占，通过项被截断 | **P0** | 待审核启事多了之后，搜图偶发漏掉已通过的正确结果 | 汉明 SQL 先 `LIMIT` 再在 Java 层过滤 audit/下架 → 名额被不可见项占满 | 把 `JOIN item` + `audit_status=1` + 状态过滤**下推进 SQL**，LIMIT 只统计可见项（缺陷#2 联带发现） | 已修复+回归 |
| 4 | 认领"拒绝"路径状态机自相矛盾 | **P0** | B、C 同时申请，拒绝 B 后物品显示"寻找中"，但 C 的申请仍"审核中" | `audit()` 拒绝分支无条件回退物品状态，未检查是否还有其他审核中申请 | 拒绝时仅当同物品已无"审核中"申请才回退；通过时自动关闭其余申请并逐个通知（附录 D4 全量重写） | 已修复+回归 |
| 5 | `reindex` 接口零鉴权 | P1 | 匿名 curl 即可触发全表 pHash 重算（DoS 面） | Controller 未调用 `requireAdmin()` | 方法首行加 `UserContext.requireAdmin()`；自动化补 403 断言 | 已修复+回归 |
| 6 | 删除启事不清理磁盘图片（孤儿文件） | P1 | 删除后 `uploads/` 残留无引用文件，越积越多 | `deleteItem` 只删库不删文件 | 删除前收集 img_url，`FileStorageService.deleteQuietly` 删原图+缩略图；连带清理 claim/message | 已修复+回归 |
| 7 | 后端 500 兜底泄露内部信息 | P1 | 异常时响应含 SQL 片段/类名（如向 multipart 接口发 urlencoded 返回 500） | `handleOther` 直接拼 `e.getMessage()`；且未处理 `HttpMediaTypeNotSupportedException` | 兜底统一"服务器繁忙"（详情仅 log）；补 Media-Type/数据约束/坏 JSON 三类友好 400 | 已修复+回归 |
| 8 | 种子脚本审核标记语义写反 | P1 | 重播后 8 条启事变"待审核"、该待审的反而已通过 | 生成脚本把"是否待审"布尔直接当 `auditStatus(0/1)` 用 | `auditStatus = 0 if (待审条件) else 1`；重播种验证分布 56 通过/4 待审 | 已修复+回归 |
| 9 | 留出查询图变换过强导致 0 命中 | P2 | 演示查询图（裁剪82%+压暗）搜不到任何结果 | 对物体居中构图，裁剪 82% 使 DCT 低频结构变化超出阈值 10 | 查询图改轻变换（裁剪90%+亮度1.05）；并由报告 11 实验确认"裁剪是 pHash 失效边界" | 已修复+回归 |

## 缺陷统计

- 发现：9（P0×4 / P1×4 / P2×1）　修复：9　遗留：0
- P0 全部集中在**核心链路**（搜图正确性×3、认领状态机×1）——与"以图搜图是亮点、认领是主线"的定位一致，修复后均有自动化断言防回归（test_api.py 中对应 TC-M3-02/03/06、TC-竞争-01/02）。
- 教训沉淀：① SQL 方言陷阱（XOR/^）写进团队规范；② multipart 文件"读一次"原则；③ 过滤条件必须在 LIMIT 之前；④ 布尔语义与状态码值严禁混用。
