# E-05（P2·后端+前端）被封禁用户的友好提示：/auth/me 区分封禁，前端专属提示

> E 批第 5 条（共 8 条）。总览与公共红线见 `00-索引与执行顺序.md` 及本文末尾。

## 现象与证据

1. **封禁表现为"莫名被登出"**：拦截器对封禁用户按匿名处理（`JwtInterceptor.java:40-42`），前端 `App.vue` 启动时 `user.refresh()` 拉 `/auth/me` 拿不到身份 → 静默 `logout()` 清 session。被封禁用户（尤其被管理员下架启事的同时被封禁的场景）只会看到"回到登录页"，**没有任何"账号已被封禁"的解释**。
2. **路由守卫不查封禁位**：`router/index.js:69-82` 只判 `logged()` 和 `role===1`。
3. **登录侧已有封禁文案**：`AuthService.java:76` 登录时封禁账号被拒绝（有提示），但已持 token 的在线用户无此待遇——两个入口口径不一致。

## 修复要求

1. **后端**：`/auth/me` 对"token 有效但 user.status=0"返回**专用业务码**（建议 `code=40301, msg="账号已被封禁，如有疑问请联系管理员"`），不再按匿名 401 处理。
   - **范围红线**：只动 `/auth/me` 这一个端点的判定；其余 `/api/**` 对封禁用户仍维持"按匿名"现状（改全局行为会影响现有 401 断言与越权测试口径，不做）。
   - 实现提示：`AuthController.me` 内部单独查一次用户状态即可，不必改拦截器。
2. **前端**：
   - `stores/user.js` 的 `refresh()` 识别 `code===40301`：清 session、写入一个短暂的"封禁提示"状态（Pinia 或 sessionStorage），跳转登录页时显示专属提示条/弹窗（ElMessage 类型 error + AuthView 顶部常驻提示条二选一），文案与后端 msg 一致；
   - 普通过期/未登录仍走现有 `clearSession()` 静默流程，不混用。
3. **单测 + 回归**：封禁用户带有效 token 调 `/auth/me` → 40301；封禁用户调其他业务接口 → 维持现有匿名口径（断言不变）；解封后 `/auth/me` 恢复正常。`test_api.py` 补 2 条断言。
4. **文档同步**：`Creator/01-交付文档/04` `/auth/me` 补 40301 码说明；`Creator/01-交付文档/01` FR1.3 "被封禁账号按未登录处理"补充"（`/auth/me` 例外，返回专用码用于前端提示）"。
