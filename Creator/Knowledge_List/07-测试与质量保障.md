## 3. 接口自测脚本（最有说服力的部分）

`backend/scripts/test_api.py` 的四个工程化设计：

- [ ] **幂等**：连跑多次八表行数回基线（不是"跑一次就脏"的脚本）
- [ ] **`try/finally` 清理**：即使中途断言失败也会删掉本次造的数据

## 6. 三个必须能讲的缺陷（★最能体现工程能力）

老师问"你们遇到过什么问题、怎么解决的"，就讲这三个，**一个有技术深度、一个有逻辑深度、一个能体现调试能力**。

### 缺陷 ①：`XOR` 与 `^` —— 搜图全 100%（P0）

| 项 | 内容 |
|---|---|
| 现象 | 所有查询结果相似度恒为 100%，完全不区分 |
| 根因 | MySQL 中 `XOR` 是**逻辑异或**（返回 0/1），`^` 才是**按位异或** |
| 修法 | 改为 `BIT_COUNT(phash ^ q)` |
| 回归 | `SearchServiceTest` + 接口断言加入"非同一物品不应 100%" |

### 缺陷 ②：先 LIMIT 后过滤 —— 结果被截断（P1，逻辑缺陷）

| 项 | 内容 |
|---|---|
| 现象 | 墙页能看到某些启事，但搜图搜不到；换一张图又能搜到 |
| 根因 | 原先 SQL 只按距离取 Top-N，再在 Java 侧过滤待审/下架 → **待审项占满名额**，把应出现的结果挤掉 |
| 修法 | 把 `audit_status=1`、`status NOT IN (...)` **下推进 SQL**，先过滤再 `LIMIT` |
| 教训 | 一切列表接口都要遵循 **"先过滤、后截断"** |

> 这个缺陷特别值钱：它不是"写错语法"，而是**顺序导致的业务错误**，且只在特定数据分布下暴露。

### 缺陷 ③：生产构建白屏（P0，F-11）

| 项 | 内容 |
|---|---|
| 现象 | `npm run build` 后页面只有米色背景，控制台 `Cannot access 'xx' before initialization` |
| 根因 | `manualChunks` 把 Element Plus **按组件首字母拆成多个 chunk** → 组件间**双向依赖跨 chunk 成环** → 循环依赖触发 TDZ（暂时性死区） |
| 修法 | element-plus 改为**单 chunk**（echarts 仍独立） |
| 教训 | **dev 正常 ≠ build 正常**；改打包配置后必须 build 后开控制台验收 |

- [ ] 能完整讲这三个（现象/根因/修法/教训）
- [ ] 至少能讲清缺陷 ① 和 ③

## 7. 缺陷分级与闭环

| 级别 | 数量 | 判定标准 |
|---|---|---|
| P0 致命/阻断 | **8** | 主流程不可用（搜图全 100%、白屏） |
| P1 严重 | **19** | 功能错误但有绕行（截断、越权、状态机错） |
| P2 一般 | **3** | 体验/文案/一致性 |
| P3 轻微 | **2** | 优化建议 |

**闭环流程**：发现（自测/评审）→ 登记（编号、现象、根因、修复方案）→ 修复 → **加回归用例** → 关闭。

> 强调"每个 P0/P1 都有回归断言"——这是"修完不会再犯"的证据。

- [ ] 能说出"闭环 = 修复 + 回归用例"，不只是"改了代码"
