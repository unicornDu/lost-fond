### 1.3 以图搜图准确率实验报告（负责人：成员E，核心加分项）★ v3.0 重写
- 【现状】`image-search.hamming-threshold: 10` 是配置直给、无实验依据；后端只算了 pHash，没有 aHash/dHash 可对比。
- 【**方法论问题（必须先解决，否则实验结论不可信）**】现有 44 张种子图看似"同物多拍"，实际只有 5 种**轻微**变换（`resize` / 居中裁剪 82% / 亮度 ×1.12 / 亮度 ×0.92 / 对比度 ×1.10 / 灰度+高斯模糊 0.8），且**同一"物"的两张图来自同一张底图**。在这类近重复样本上，aHash/dHash/pHash 都会拿到接近满分，**实验表会"太漂亮"反而不可信**；同时现在只有 4 张留出查询图 `q-1/3/5/7.jpg`，**没有负样本，画不出 P/R 曲线**。
- 【做法】
  1. `PHashUtil` 增加 aHash/dHash（JImageHash 原生支持 `AverageHash` / `DifferenceHash`）；
  2. **先把种子图做强（依赖 2.12）**：每物至少 5 张真实变体，引入**旋转**（±5°/±10°）、**换背景/换拍摄距离**、**低质量 JPEG 重压缩（q=30）**、**不同裁剪比例**、**运动模糊**；
  3. **构造带标注的查询集**：正样本 = 同物变体；**负样本 = 同类别不同物**（如"另一个保温杯""另一副白耳机"），这是老师最容易追问的点；
  4. 在阈值 4/6/8/10/12 下统计三种哈希的 Precision / Recall / F1，出对比表 + 曲线图（含"阈值—误报率/漏报率"权衡图）；
  5. 结论回填 `application.yml` 的 `hamming-threshold`，并在报告中说明"为什么最终选 X"。
- 【验收】docs/ 新增 `11-以图搜图准确率实验报告`：含**正负样本集说明**、数据表、曲线图；阈值有实验出处且与 `application.yml` 一致。

### 2.3 演示管理员与演示账号无法登录（P0）

### 2.4 审核流水位决策：`audit_status` 恒为 1 会让后台审核页永远为空（P0，v3.0 新增）
- 【现状】`ItemService.publish()` 第 57 行硬编码 `item.setAuditStatus(1)`，`DataInitializer` 第 130 行同样 `setAuditStatus(1)`。实测：**22 条启事全部 `audit_status = 1`，`audit_status = 0` 的记录数为 0**。
- 【后果】2.9 的管理后台做完后，"待审核列表"打开是空的，**"审核通过/驳回"这两个动作演示时无数据可点**。这是 v2.0 执行顺序里会直接踩的坑。
- 【做法】二选一，并写进文档与答辩稿：
  - **① 走真审核流（推荐）**：`publish` 改为 `setAuditStatus(0)`；`ItemService.list()` 已按 `eq("audit_status", 1)` 过滤，前台不受影响，管理后台立刻有待审数据。需补一条 `UPDATE item SET audit_status = 0 WHERE id IN (...)` 造 3–5 条演示数据（或直接纳入 2.10 的种子脚本）。
  - **② 保留"先发布后审核"**：明确说明"审核是事后抽检机制"，并在种子数据里手工造 3–5 条 `audit_status = 0` 用于演示。
- 【验收】后台"待审核"标签页有 ≥3 条数据，审核通过/驳回各演示一次；前台列表不受影响。

### 2.5 认领审核是"盲审"，防冒领主线走不通（P0）

  - 前端 `ProfileView`"收到的申请"里，发布者只能看到物品名和状态，**看不到任何凭证就只能凭感觉点通过/拒绝**；
  - `DetailView.vue` 第 40 行 `applyClaim(item.value.id, { proof: claimText.value.trim() })`，认领弹窗（第 112–120 行）**只有凭证文本框、没有联系方式输入框**，`ClaimReq.contact` 从未被前端赋值。

  2. `ClaimService.build()` 批量查申请人信息回填（参考 `ItemService.loadNicknames` 的批量查法）；

  4. 认领弹窗加"联系方式（选填）"输入项并随 `applyClaim` 一起提交。

### 2.6 认领状态机漏洞（P0，v3.0 扩充：补「拒绝」路径）
- 【现状·通过路径】同一物品可被多人申请；通过 A 后，B、C 的申请仍停留"审核中"且收不到通知；更严重的是 `ClaimService.audit()` 只校验申请自身状态、**不校验物品是否已认领**，发布者回头还能再通过 B，产生**两条"已通过"记录**。
- 【现状·拒绝路径（v3.0 实测复现）】`audit()` 拒绝分支第 83 行**无条件**把物品状态改回 `寻找中/待认领`，完全不管同物品是否还有其他"审核中"申请。实测：
  ```
  A 发布启事 → B、C 同时申请 → item.status = 认领申请中   ✓ 正常
  A 拒绝 B 的申请            → item.status = 寻找中      ✗ 但 C 的申请仍是「审核中」
  ```
  界面显示"寻找中"，实际却挂着一条待审申请，状态机自相矛盾。
- 【现状·申请入口守卫过窄】`apply()` 第 42 行只挡了"已认领/已找回"，**已下架/已关闭的启事仍可被申请认领**。
- 【做法】
  1. `audit()` 开头加物品状态守卫（`已认领/已找回` 直接拒）；

### 2.18 关键词检索：文档与实现不一致（P1）
- 【现状】`schema.sql` 第 53 行建了 ngram 全文索引 `ft_title_desc`，但 `ItemService.list()` 第 108 行实际用 `like("title", k).or().like("description", k)`。**实测 `EXPLAIN`**：走的是 `Index scan on item using idx_create_time (reverse)` + `Filter: title like '%abc%'`，**全文索引完全未被使用**。
- 【做法】二选一：① 改 `MATCH(title,description) AGAINST(? IN NATURAL LANGUAGE MODE)`（需手写 Mapper SQL，MyBatis-Plus `QueryWrapper` 不支持全文语法）；② 保留 LIKE，并在 `schema.sql` 与 `06-数据库设计` 中删去全文索引或注明"数据量小，LIKE 足够"。**不要留着"文档说了但代码没做"的状态。**
- 【验收】实现与 `06-数据库设计` 文档一致。

  - 上传**无体积校验**（只有 `accept="image/*"`），手机原图 10MB+ 撞上 `api/index.js` 第 23 行的 `timeout: 20000` 极易超时且无进度提示。
- 【做法】① 改 `value-format="YYYY-MM-DD HH:mm:ss"` 并删掉 `fmtTime()`，直接 `fd.append('happenTime', form.time)`；② 两个提交函数首行加 `if (submitting.value) return`，或改 `:disabled="submitting"`，并删掉死代码分支；③ 加 `beforeUpload` 体积校验（≤5MB）+ 上传进度条。
- 【验收】快速双击只产生 1 条启事；选 10MB 图被前端拦下并提示；发布日期与所选一致（换时区测试）。

### 2.28 `ItemForm` 缺长度校验 + 后端静默兜底（P1，v3.0 新增）
- 【现状】`ItemForm` 只有 `type`/`title` 有 `@NotBlank`，**没有任何 `@Size`**；而 DB 列宽是 `title VARCHAR(60)`、`category VARCHAR(20)`、`location VARCHAR(50)`、`description VARCHAR(500)`。超长直接抛 `DataIntegrityViolationException` → 被 `GlobalExceptionHandler` 的兜底分支接住，返回 `"服务器开小差了：" + e.getMessage()`（**顺带泄露 SQL 信息**，正是 2.24 提到的问题）。
  另有两处静默污染，比报错更糟：`ItemService.parseTime()` 遇非法日期**静默改成当前时间**；`setType("found".equals(type) ? "found" : "lost")` 把任意非法值**静默变成 lost**。
- 【做法】① `ItemForm` 补 `@Size(max=60/20/50/500)`，`type` 加 `@Pattern(regexp = "^(lost|found)$")`；② `happenTime` 解析失败改为抛 `BusinessException("时间格式不正确")`；③ `GlobalExceptionHandler` 增加 `DataIntegrityViolationException` 与 `HttpMessageNotReadableException` 处理器，返回友好 400。
- 【验收】提交 100 字标题被 400 拦下并提示；`type=hack`、`happenTime=abc` 均被拒；不再出现 500 兜底文案。

### 2.29 认证纵深：登录限流、登出吊销、`admin_log` 读取入口（P1，v3.0 新增）
- 【现状】① `/api/auth/login` 无失败次数限制，可无限爆破（BCrypt 只拖慢单次成本）；② **没有 logout / 令牌吊销接口**，前端登出只清 localStorage，令牌在 7 天 TTL 内始终有效（2.24 只讲了"封禁延迟"）；③ `admin_log` **全项目唯一用法是 `insert`**（`AdminService` 第 112 行），没有任何查询接口 → 七个管理动作都留了痕，但谁也看不到。
- 【做法】① 登录失败计数（内存 `ConcurrentHashMap<账号, 失败次数+锁定时间>`，5 次锁 10 分钟）即可，无需引入 Redis；② 报告中明确写"JWT 无状态、无服务端登出，登出仅清客户端令牌"的取舍，或给 `user` 表加 `token_version` 做轻量吊销；③ ★ **最省力且加分**：2.9 的后台加一个"操作日志"页，`GET /api/admin/logs` 分页读 `admin_log`（字段齐备，零额外写入逻辑）。
- 【验收】连续错 5 次密码被锁定并提示；后台能翻看管理操作日志。

### 2.30 首页统计口径错误 + 落地页硬编码假数据（P1，防穿帮）
- 【现状】① `StatsService.homeStats()` 的 `lostCount` 用 `eq("type","lost").eq("audit_status",1)` 统计，**把"已找回"的也算进了"寻找中"**。实测：`lostCount = 13`，而真正还在找的只有 **11** 条。② `WelcomeView.vue` 整页写死"1,286 名同学""本学期已帮 128 件失物找到主人""98.2% 找回满意度"，而首页真实 `api.stats()` 显示 `reunited:4 / lost:13 / found:9`（用户总数 19）。
- 【后果】答辩时老师对照落地页与首页数字就能看出对不上，属于"一眼穿帮"。
- 【做法】① `homeStats` 的 lost/found 计数加 `status NOT IN ('已找回','已认领')` 条件（或把语义改成"累计"并在标签上写清）；② 落地页所有数字接 `api.stats()`，接不了的（如满意度）改定性文案或明确标注"示意数据"。
- 【验收】落地页与首页数字一致；"寻找中"计数与墙上实际条数对得上。

### 2.31 前端健壮性包（P1–P2，v3.0 新增）
- 【现状】
  - **读取类接口失败全部静默**：`HomeView` 第 23–25 行、`WallView` 第 33–35 行、`ProfileView` 第 32–34 行、`DetailView` 第 27–30 行只 `console.error`，页面退化成空态——用户无法区分"没数据"和"后端挂了"（2.14 只覆盖了 401）；

### 2.32 `views` 非原子自增 + `idx_phash` 是无效索引（P2，v3.0 新增，报告素材）
- 【现状】① `ItemService.detail()` 是"读出来 +1 再写回"，并发下会丢更新，且 **GET 请求写库**导致详情页不幂等（2.36 的 2.21 只提了"无去重"）；② `schema.sql` 第 67 行建了 `KEY idx_phash (phash)`，但 `BIT_COUNT(phash ^ ?)` 是函数作用在列上，**该索引永远不会被选中**。
- 【实证】`EXPLAIN`：以图搜图走 `Index scan on item_image using idx_item` 全扫 44 行，`idx_phash` 未出现。
- 【做法】① `views` 改 `UPDATE item SET views = views + 1 WHERE id = ?` 原子自增；② 在 2.18/2.33 里补一句：`idx_phash` 当前是**无效索引**，可删，或保留并注明"为未来分段前缀索引预留"。写进报告"索引设计"一节是很好的加分点。
- 【验收】报告中有该索引的取舍说明；并发刷新浏览量不再丢计数。

### 2.38 错误响应统一返回 HTTP 200 的取舍说明（P2，v3.0 新增）
- 【现状】全站错误都返回 **HTTP 200**，业务码塞在 body 的 `code` 字段。实测：`/api/items/999999` → `HTTP 200` + `{"code":404,"msg":"启事不存在或已被删除"}`；未登录 → `HTTP 200` + `{"code":401}`。
- 【做法】这是既定设计（前端 axios 拦截器按 `body.code` 判定），**不必改**，但建议：① 在报告"接口设计"一节主动写明取舍（统一响应包装的利弊）；② 或在 `Result` 上按 code 加 `@ResponseStatus` 映射，让 HTTP 状态码与业务码一致，更符合 RESTful。二选一，**主动说明优于被问住**。
- 【验收】报告有该设计决策的说明。

```java
    if (!"审核中".equals(c.getStatus())) throw new BusinessException("该申请已处理过");
    // ★ 新增①：物品已完成认领则不再受理
    if ("已认领".equals(item.getStatus()) || "已找回".equals(item.getStatus()))
        throw new BusinessException("该物品已完成认领，申请已关闭");

    boolean lost = "lost".equals(item.getType());

    if (req.isApprove()) {
        c.setStatus("已通过");
        c.setReply(blankTo(req.getReply(), "已通过认领，请联系交接"));
        claimMapper.updateById(c);

        item.setStatus(lost ? "已找回" : "已认领");
        itemMapper.updateById(item);

        // ★ 新增②：关闭同物品其余"审核中"申请并逐个通知
        List<ClaimRecord> others = claimMapper.selectList(new QueryWrapper<ClaimRecord>()
                .eq("item_id", c.getItemId()).eq("status", "审核中").ne("id", c.getId()));
        for (ClaimRecord o : others) {
            o.setStatus("已拒绝");
            o.setReply("物品已被其他申请人认领");
            claimMapper.updateById(o);
            push(o.getClaimantId(), "claim", "认领申请未通过",
                 "你对「" + item.getTitle() + "」的申请未通过：物品已被其他申请人认领。", item.getId());
        }
        push(c.getClaimantId(), "claim", "认领申请已通过",
             "你对「" + item.getTitle() + "」的认领申请已通过：" + c.getReply(), item.getId());

    } else {
        c.setStatus("已拒绝");
        c.setReply(blankTo(req.getReply(), "特征不符，已拒绝"));
        claimMapper.updateById(c);   // ★ 关键：先落库，下面的计数才会排除自身

        // ★ 新增③：仅当已无其他"审核中"申请时才回退物品状态
        Long pending = claimMapper.selectCount(new QueryWrapper<ClaimRecord>()
                .eq("item_id", c.getItemId()).eq("status", "审核中"));
        if (pending == null || pending == 0) {
            item.setStatus(lost ? "寻找中" : "待认领");
            itemMapper.updateById(item);
        }
        push(c.getClaimantId(), "claim", "认领申请未通过",
             "你对「" + item.getTitle() + "」的认领申请未通过：" + c.getReply(), item.getId());
    }
}
```
