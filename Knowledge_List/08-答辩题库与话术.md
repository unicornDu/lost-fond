## 一、开场三问（一定会问）

**【问】用一分钟介绍你的项目。**
**【答】** 校园失物招领平台。痛点是传统平台靠文字描述搜索，"黑色钱包"这种描述说不清也搜不准。我们的做法是**以图搜图**：用户上传一张照片，系统把图片压缩成 64 位感知哈希指纹，用 MySQL 的 `BIT_COUNT(phash ^ q)` 算汉明距离，阈值 12 以内判为相似，按相似度取 Top-10。实测召回 85.7%、误检 0、单张 41~54 毫秒。技术上后端 Spring Boot 3.3 + MyBatis-Plus + MySQL 八表，前端 Vue3 + Vite，一套代码跑 Web / Android / iOS PWA / 桌面 Electron 四端。

## 二、以图搜图专项（最容易被深挖）

**【问】以图搜图的原理？**
**【答】** 感知哈希。五步：灰度化 → 缩到 32×32 → DCT 变换到频域 → 取左上 8×8 低频 → 按均值二值化，得到 64 位指纹。比对用汉明距离 = `Long.bitCount(a ^ b)`，相似度 = `(1 - 距离/64) × 100%`，距离 ≤ 12 判相似，按距离升序取 Top-10。

**【问】为什么不用 MD5 之类的哈希？**
**【答】** MD5 有雪崩效应，改一个字节结果就面目全非，**无法比较相似度**。感知哈希是从图像结构提特征，视觉相似则指纹相近，这正是我们需要的性质。

**【问】为什么阈值是 12？**
**【答】** 两套实验互证。① 真实种子库端到端网格扫描：top-n=6 时召回只有 53.6%~60.7%，改成 top-n=10/th=12 后 85.7% 且误检 0；② 受控变体库里 th=12 是 pHash 在 mild 组的 F1 峰值（0.833）。再往上到 14/16，召回升到 89.3%/96.4% 但已贴近跨物体误检区，返回列表也变长，所以取 12。
**【别说】** "试出来的""凭经验定的"。

**【问】那 Top-N 为什么是 10？**
**【答】** 因为瓶颈在截断不在算法：top-n=6 时同阈值下召回只有 60.7%，top-n 提到 10 立刻到 85.7%，再往上（20、50）完全没变化——说明 6 条是硬截断。取 10 是"召回拉满 + 列表不至于太长"的折中。

**【问】一张图和一个启事多张图，距离怎么算？**
**【答】** `GROUP BY item_id` 后取 `MIN(距离)`，即"这条启事里最像的那张图"的距离。发布支持 1~3 张不同构图，正是为了提高命中面。

**【问】旋转的图片能搜到吗？**
**【答】** 不能。这是 pHash 的已知边界：DCT 对方向敏感，旋转会打乱低频布局。实测旋转 5° 召回 0.33，10° 直接归零。工程上我们做了三点缓解：多图入库、拍摄引导"拍满物品"、演示素材只用鲁棒变换。彻底解决需要旋转不变特征或多角度入库，写在报告的展望里。
**【别说】** "能搜到"或"我们的算法很鲁棒"——一测就露。

**【问】裁剪呢？**
**【答】** 也弱。裁剪 85% 时 pHash 召回为 0；裁剪 70% 时**三种哈希全部归零**——说明这是感知哈希家族的共性局限，不是选型问题。这个结论在报告里有明确数据支撑。

**【问】你的表里 aHash 分数比 pHash 高，为什么还选 pHash？**
**【答】** 这是 6 个对象小库上的结果，aHash 在 mild t=10 是 0.867、pHash 是 0.800。但 aHash 的宽容是**用区分度换来的**——阈值升到 12 时它出现 Precision(0.798) < Recall(0.810) 的跨物体误检分化，库越大误检越多；而 pHash 在缩放、压缩场景稳定 100%、误检最少，与文献共识一致。我们也诚实承认：本实验规模不足以给出统计显著结论。
**【别说】** "pHash 准确率最高"——数据不支持，会被抓。

**【问】核心 SQL 怎么写的？**
**【答】** 一条 SQL 算完：
`SELECT ii.item_id, MIN(BIT_COUNT(ii.phash ^ #{q})) AS dist FROM item_image ii JOIN item i ON i.id=ii.item_id WHERE ii.phash IS NOT NULL AND i.audit_status=1 AND i.status NOT IN ('已下架','已关闭') GROUP BY ii.item_id HAVING dist <= #{threshold} ORDER BY dist ASC LIMIT #{limit}`。
两个关键点：`^` 是按位异或、`BIT_COUNT` 数不同位数；审核/下架过滤必须下推进 SQL。

**【问】为什么要放进 SQL 里过滤，不能查出来再过滤？**
**【答】** 踩过这个坑。原先先在 SQL 取 Top-N 再在 Java 侧过滤，结果**待审核条目占满了 Top-N 名额**，把本该出现的结果挤掉，导致"墙页能看到但搜图搜不到"。改成先过滤再 `LIMIT` 就正常了。原则：先过滤、后截断。

**【问】`XOR` 和 `^` 有什么区别？**（陷阱）
**【答】** MySQL 里 `XOR` 是**逻辑异或**，只返回 0/1；`^` 才是**按位异或**。我们早期误用 `XOR`，导致所有距离≈0、相似度全 100%，是缺陷跟踪表里的第一条 P0。

**【问】一万张图还能这么快吗？**
**【答】** 不能线性外推。当前是 `item_image` 全表 `BIT_COUNT` 扫描，千级以内几十毫秒够用；万级要上优化：① 64 位拆 4×16 位做分段哈希前缀粗筛；② 倒排/BKD 多列索引；③ 换 CNN 特征 + 向量库做 ANN 近似检索。**普通 B-Tree 索引对汉明距离无效**，因为它是按位异或后的计数，不是范围比较。

**【问】pHash 为什么存 BIGINT 不存字符串？**
**【答】** 64 位正好等于 BIGINT/long 宽度，8 字节；字符串要 64 字节还得在 Java 侧解析。存整数可以让 `^` 和 `BIT_COUNT` 在库内一次算完，省空间又可比对。

## 三、后端专项

**【问】讲一下登录鉴权的完整流程。**
**【答】** 登录成功签发 JWT（sub=userId、role、过期时间，HMAC 签名）→ 前端存 localStorage → axios 拦截器加 `Authorization: Bearer` → 后端 `JwtInterceptor` 验签、**查库校验用户状态**、把 uid/role 写进 ThreadLocal（`UserContext`）→ Service 用 `requireUserId/requireAdmin` → 请求结束 `afterCompletion` 清理 ThreadLocal。

**【问】为什么用 JWT 不用 Session？**
**【答】** 无状态、服务端不存会话、加机器不用同步、跨端友好（一个请求头，Web/桌面/App 通用）。代价是不能主动注销，所以我们在拦截器里每次请求查一次用户 status，实现"封禁/删除实时生效"。

**【问】那你们怎么实现"登出"？**
**【答】** 前端删 token，服务端不存会话所以不做处理；真正需要立刻失效的场景（封禁）靠查库。要说彻底解决得有 Redis 黑名单。**这是 JWT 的固有取舍，我们不假装它没有代价。**

**【问】ThreadLocal 为什么必须清理？**
**【答】** Tomcat 线程池会复用线程，不清理会导致下一个请求读到上一个用户的身份，造成越权串号。所以必须在 `afterCompletion` 清理（`postHandle` 不行，异常时它不执行）。

**【问】单例 Bean 有没有线程安全问题？**
**【答】** 有隐患。`@Service` 默认单例，多个请求共享同一个实例，**所以不能把请求相关的数据放成员变量**——这正是我们用 ThreadLocal 而不是 `this.currentUser` 的原因。

**【问】密码怎么存？**
**【答】** BCrypt，单向加盐，同密码每次结果不同，登录用 `matches` 校验。不存明文也不存 MD5（MD5 无盐、可彩虹表、算得太快）。

**【问】怎么防暴力破解？**
**【答】** 三层：登录限流（同账号连错 5 次锁 10 分钟）、BCrypt 加盐、封禁后 token 实时失效。要指出的是限流是**内存计数，多实例部署会失效**，生产要换 Redis 滑动窗口。

**【问】文件上传怎么防漏洞？**
**【答】** 七道关：扩展名白名单 → **文件头魔数校验**（jpg 是 FF D8 FF、png 是 89 50 4E 47，webp 单独校验 RIFF....WEBP）→ 大小 5MB → UUID 重命名 → 按年月分目录 → 路径不越界 → 生成 480px 缩略图。只看扩展名会被"exe 改名成 jpg"骗过，魔数才拦得住。

**【问】SQL 注入怎么防？**
**【答】** MyBatis 的 `#{}` 是预编译占位符，传值不参与 SQL 拼接；`${}` 是字符串拼接，禁止用于用户输入。本项目所有查询都走 `#{}` 或 QueryWrapper 参数化。

**【问】事务用在哪？**
**【答】** 两处必须：发布（item + 多条 item_image 原子，否则出现"有启事没图"）、认领审核（claim + item + message + delivery）。另外说明一个取舍：认领证明 PDF 生成失败**只记日志不回滚审核**，主流程不能被附件拖垮。

**【问】事务失效的情况知道吗？**
**【答】** 常见三种：同类内部方法自调用（不走代理）、方法不是 public、异常被 catch 掉没抛出去；还有默认只对 RuntimeException 回滚。

## 四、数据库专项

**【问】有几张表，什么关系？**
**【答】** 八张。user→item→item_image（一对多）、item→claim_record←user（申请人）、item→delivery，user→message/admin_log/favorite。核心是 `item_image.phash` 这个 64 位指纹，它是以图搜图的根。

**【问】item 表为什么有两个状态字段？**
**【答】** `status` 是业务流转（寻找中/待认领/认领申请中/已找回/已认领/已下架/已关闭），`audit_status` 是内容治理（0 待审/1 通过/2 驳回），两者正交。只有 `audit_status=1` 才上墙、才能被搜图命中。

**【问】两个人同时申请认领怎么办？**
**【答】** 竞争状态机：发布者通过 A 时，自动把同 item 其余"审核中"置为已拒绝并逐个通知，所以不可能两人同时认领成功；拒绝某条时，只有没有其他在审申请才把物品回退到原状态，否则保持"认领申请中"。

**【问】索引建了哪些，为什么？**
**【答】** `item(type,status)` 联合索引服务墙页筛选、`category`、`user_id`、`create_time` 各一个，`user.account` 唯一索引防重复注册。**故意没做的两个**：`phash` 上没建能加速搜索的索引（汉明距离是位运算计数，B-Tree 用不上）、没做全文索引（千级数据 `LIKE` 够快，ngram 维护成本高收益小）。

**【问】为什么图片不存数据库？**
**【答】** BLOB 会撑爆库、备份臃肿、无法走静态资源；存路径 + 指纹更灵活，图片由后端映射成 `/uploads/**` 直接访问。

**【问】删除启事怎么处理关联数据？**
**【答】** `delivery` 按 `biz_id` 级联删行 + 删磁盘文件；图片要按**引用计数**删——种子数据里 30 个去重文件被 120 条引用复用，直接删会误伤别人的启事。

## 五、前端与多端专项

**【问】一套代码怎么跑四端？**
**【答】** 差异只有三点：路由模式、资源地址、登录态持久化。桌面（`file://`）和 Android（`https://localhost`）用 **hash 路由**（history 刷新会 404），用 `assetUrl()` 把 `/uploads/*` 拼成后端绝对地址；原生端登录态以 Capacitor Preferences 为真源、localStorage 做镜像。业务代码零分叉，适配收在 `utils/desktop.js`。

**【问】路由守卫做了什么？**
**【答】** 四条：非公开页未登录 → 跳登录并记住来源；已登录访问 `/auth` → 回首页；非管理员访问 `/admin/*` → 回首页；`afterEach` 按 `meta.title` 设标题。要强调**前端守卫只是体验，真正校验在后端**，改前端或直接调接口都能绕过。

**【问】axios 拦截器干什么？**
**【答】** 请求拦截加 token；响应拦截统一剥 `{code,msg,data}` 外壳，`code=200` 直接返回 data，`401` 清登录态并跳登录页，其他抛错让页面提示。

**【问】Pinia 里为什么还要 localStorage？**
**【答】** Pinia 是内存态，刷新就没了；localStorage 是持久层，启动时用它恢复。

**【问】你踩过最深的坑？**
**【答】** 生产构建白屏（F-11）。`manualChunks` 把 Element Plus 按组件首字母拆成多个 chunk，组件间双向依赖**跨 chunk 成环**，触发 TDZ，报 `Cannot access 'xx' before initialization`，Vue 没挂载，页面只剩背景色。改成单 chunk 解决。教训是 **dev 正常 ≠ build 正常**，改打包配置必须 build 后用控制台验收。

**【问】ECharts 看板怎么做的？**
**【答】** 两张图：每日发布趋势折线 + 分类占比环形，数据来自 `/api/admin/stats`。三个必备动作：`init` → `setOption` → 卸载时 `dispose`；容器要有明确高度，窗口 resize 要调 `chart.resize()`。

**【问】Electron 为什么这么大？**
**【答】** 它把整个 Chromium + Node 运行时打进去了，`win-unpacked` 里能看到 `chrome_*.pak`、`ffmpeg.dll`。这是"一套 Web 代码出桌面版"的代价，更轻的替代是 Tauri（用系统 WebView）。同时我们做了 `contextIsolation: true` + 预加载白名单，渲染层碰不到文件系统。

## 六、测试与工程专项

**【问】你们怎么测的？**
**【答】** 四层：后端单测 99 个（JUnit）、接口自测 141 断言（Python + requests）、前端 12 个 vitest、算法实验 + 端到端召回评测。测试用例 91 条，覆盖功能/边界/异常/越权。累计发现 32 个缺陷，全部闭环且 P0/P1 都补了回归断言。

**【问】接口脚本有什么讲究？**
**【答】** 四个设计：幂等（连跑多次八表回基线）、`try/finally` 清理（失败也删造的数据）、自报断言总数（防漏跑）、退出码非 0 判失败（可接 CI）。

**【问】怎么保证改了算法不退化？**
**【答】** 有召回门禁：`eval_recall.py --min-recall 0.75`，低于阈值直接失败。改阈值或 Top-N 必须重跑。

**【问】项目有什么不足？**
**【答】** 主动说五个：覆盖率没做统计、前端自动化测试薄（只 12 个）、性能只做了 20 并发的手工验证没有压测工具、实验规模小（6 对象 72 查询不具统计显著性）、没有 CI。**每条都给出"要补会怎么做"**。
**【别说】** "没什么不足"或"时间不够所以没做"——前者显得没反思，后者像找借口。

**【问】如果再做一次，你会改什么？**
**【答】** 三个优先级：① 先补 CI（脚本都写好了，接 GitHub Actions 成本很低）；② 前端交互补 e2e 测试；③ 算法上试旋转不变特征或多角度入库，把旋转这个已知边界补上。

## 七、陷阱题专区（这些最容易翻车）

| 陷阱问法 | 错误答法 | 正确答法 |
|---|---|---|
| "你们用的是 CNN/深度学习吗？" | 含糊说"用了 AI" | **明确说不是**：纯 Java 实现的感知哈希，不依赖任何 AI 服务、可离线跑。选它是因为课程周期内可控、可解释、可实验标定 |
| "aHash 分更高为什么不用？" | "pHash 更准" | 见第二节，讲区分度/误检/文献共识 + 承认规模不足 |
| "旋转能搜到吧？" | "能" | 不能，给数字（5°→0.33，10°→0）和三条缓解 |
| "JWT 能主动踢人下线吗？" | "能" | 不能，靠每次查库 status 实现封禁实时生效；彻底解决需 Redis 黑名单 |
| "限流是分布式的吗？" | "是" | 内存计数，多实例会失效，这是已知局限 |
| "给 phash 建索引就快了吧？" | "对，建了索引" | 汉明距离是位运算计数，普通索引无效；规模化要走分段哈希/向量库 |
| "审核过滤为什么不在 Java 里做？" | "在 Java 做也行" | 会导致 Top-N 名额被待审项占满，必须下推 SQL |
| "你们四个人都写代码吗？" | 全说"是" | 按角色如实说，但**每人要能讲清自己那块的细节**（文档岗也要能讲 UML/ER） |

| 时间 | 动作 | 讲解词 |
