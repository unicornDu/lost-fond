## 1. 一句话说清项目

> 面向校园场景的失物招领平台，核心创新是**以图搜图**：丢东西的人拍张照片上传，系统靠"图片长相"（感知哈希 pHash）在全校启事里找出可能是同一件物品的条目，不依赖文字描述是否准确。

**要解决的问题**：传统失物招领靠文字搜（"黑色钱包"），用户说不清、搜不准；而手机里本来就有物品照片。

- [ ] 能用 30 秒向老师讲清"痛点 → 方案 → 亮点"

## 2. 用户角色与权限

| 角色 | role | 能做什么 | 不能做什么 |
|---|---|---|---|
| 游客 | — | 落地页、登录注册 | 任何业务操作 |
| 普通用户 | 0 | 发布启事、搜图、认领、私信、收藏、个人中心 | 看到未过审内容、进后台 |
| 管理员 | 1 | 审核/驳回/下架/删除、用户封禁⇄解封、看板、操作日志、运维工具（重算哈希/重建缩略图/导报表） | — |

**双层防护**（重要，老师爱问）：

- 前端：路由守卫 `meta.roles:['admin']`，非管理员访问 `/admin/*` 直接回首页。
- 后端：`UserContext.requireAdmin()` 非管理员抛 403。
- 为什么两层都要：**前端守卫只是体验，真正的安全边界在后端**；改前端代码或直接调接口都能绕过前者。

## 4. 非功能需求（NFR，答辩常被追问）

| 编号 | 指标 | 达成情况 |
|---|---|---|
| NFR-1 | 搜图响应 < 2s | 实测 41~54ms（120 图索引），远低于指标 |
| NFR-3 | 20 并发搜图结果一致 | 实测 20 并发总 132ms，全部 code=200、结果一致 |
| 上传 | 单图 ≤ 5MB | `application.yml` 限制 + 前端上传前拦一道 + 后端魔数校验 |
| 列表 | 单页上限 100 条 | 防"拉全库"式拖库 |
| 密码 | 不存明文 | BCrypt 单向加盐 |
| 演示数据 | 可重置 | TRUNCATE 八表 → 重启后端自动播种 |

## 7. 架构与端口（★能画出来）

```
浏览器
        │  HTTP
        ▼
Vite dev :5173 ──proxy──┐        （开发期；生产直接由后端托管 dist）
                        │
                        ▼
              Spring Boot :8080  ── JDBC ──▶  MySQL :3306 (lost_found，八表)
                        │
                        └── 磁盘 web-lostfond/backend/uploads/**  ←映射为→  /uploads/**
```

- 开发期前端连自己的 5173，Vite `proxy` 把 `/api`、`/uploads` 转给 8080 → **浏览器视角同源，无跨域**。
- 后端另有 `CorsConfig` 显式来源放行（生产默认收紧）；本项目同源部署通常不触发 CORS。
- 生产：`npm run build` → `frontend/dist`，后端 `/**` 直接托管 + SPA 回退（`FrontendController`），所以 `http://localhost:8080` 就是完整站点。

- [ ] 能解释"为什么开发期不会跨域、生产期也不会"（开发期代理同源；生产同源部署）

## 8. 后端分层与真实规模

```
Controller（8）  收参、校验、调 Service、包 Result —— 不写业务
   ↓
Service（12）    业务逻辑、事务边界、状态机
   ↓
Mapper（8）      BaseMapper 单表 CRUD + @Select 写复杂 SQL
   ↓
MySQL（8 表）
```

| 层 | 数量 | 说明 |
|---|---|---|
| controller | **8** | Auth / Item / Search / Claim / User / Admin / File / Frontend |
| service | **12** | Auth / Item / Search / Claim / User / Admin / Message / Stats / FileStorage / FileDelivery / Pdf / Favorite |
| mapper | **8** | 与八表一一对应，`ItemImageMapper`、`ItemMapper` 有自定义 SQL |
| entity | **8** | User / Item / ItemImage / ClaimRecord / Message / AdminLog / Favorite / Delivery |
| dto / vo | **9 / 5** | 入参带校验注解；出参只暴露安全字段 |
| config | **7** | Cors / WebMvc / MybatisPlus / SecurityBeans / JwtProperties / FileProperties / ImageSearchProperties |

**为什么 entity / dto / vo 要分三种**（常考）：

- entity 贴表，含 `password` 等敏感列 → **绝不直接返回前端**
- dto 贴"前端传什么"，带 `@NotBlank/@Size/@Pattern`
- vo 贴"前端要什么"，字段安全且可加工（如 `ItemVO` 里加 `similarity`、把 `user_id` 换成昵称）

> 一句话：**改表不影响接口，改接口不影响表。**

- [ ] 能说出"8 个控制器 / 12 个服务 / 8 张表"这组数字
- [ ] 能举一个 entity 不能直接返回的例子（`User.password` 是 BCrypt 密文）

## 9. 一次请求的完整链路（以"以图搜图"为例，能背下来）

```
① 用户在 SearchImageView 选图
② POST /api/search/image  (multipart)
③ JwtInterceptor 先过：解析 Authorization: Bearer → 查库校验 status → 写入 UserContext(ThreadLocal)
④ SearchController 收 MultipartFile，转 byte[]
⑤ SearchService.searchByImage：
     PHashUtil.hash(bytes) → q（64 位 long）
     ItemImageMapper.searchByHash(q, 12, 10)  ← 一条 SQL 算完：过滤+汉明距离+Top-10
⑥ 逐条转 ItemVO，similarity = (1 - dist/64) × 100
⑦ Result.ok(list) → JSON {code:200,msg,data}
⑧ 前端响应拦截器剥掉外壳，页面渲染卡片 + 相似度进度条 + 耗时
⑨ afterCompletion：UserContext.clear()  ← 防线程复用串号
```

- [ ] 能指出这条链路里"哪一步最容易出问题"（第 ⑤ 步的 SQL；第 ⑨ 步的 ThreadLocal 清理）

## 10. 关键配置（`application.yml`，改参数只看这里）

```yaml
server.port: 8080
image-search:
  bit-resolution: 64
  hamming-threshold: 12     # 判"同一物品"的红线
  top-n: 10                 # 返回条数
file:
  upload-dir: uploads       # ★ 相对路径 → 必须在 backend 目录启动
  max-size: 5MB
jwt:
  header: Authorization
  prefix: "Bearer "
  expire: 1440              # 分钟（记住我 → 30 天）
```

**敏感配置在 `application-local.yml`**（gitignored）：数据库口令、`jwt.secret`、`seed.admin-password`、`seed.user-password`。`application.yml` 里只有 `${DB_PASSWORD:}` 这类占位符。
