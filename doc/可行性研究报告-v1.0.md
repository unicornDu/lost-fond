## 1. 引言

### 1.1 编写目的
在项目立项与设计之前，从**技术、经济、操作、法律、进度**五个维度论证"基于感知哈希（pHash）的校园失物招领平台"的可行性，回答两个问题：这件事值不值得做；以本小组的能力与资源能不能按时做成。

### 1.2 项目背景
校园失物招领的普遍痛点是**"文字描述搜不准"**：失主用"黑色卡包"描述物品，拾主可能写"钱包/卡套"，关键词永远对不上。市面同类系统（GitHub 开源项目调研，2026-09-28，见 `other/other/Creator/过程资料/选题/失物招领-参考项目与前端模板.md`）几乎全部是"文字搜索 + CRUD"形态，**没有以图搜图能力**——这正是本项目的差异化切入点。

### 1.3 术语
| 术语 | 说明 |
|---|---|
| pHash | 感知哈希（Perceptive Hash），图片缩放→灰度→DCT→取低频→二值化得到的 64 位指纹；同物照片指纹相近 |
| 汉明距离 | 两个等长比特串中不同位的个数；本项目用 SQL `BIT_COUNT(a ^ b)` 直接计算 |
| JWT | JSON Web Token，无状态登录令牌 |
| M1–M7 | 模块编号：用户/发布/以图搜图/检索/认领消息/管理后台/守望订阅 |

### 1.4 参考资料
《01-需求规格说明书》《03-项目计划书》《11-以图搜图准确率实验报告》（同目录）；JImageHash 官方文档（dev.brachtendorf:JImageHash 1.0.0，Maven Central）。

## 2. 项目概述

**做什么**：一个 Web 版校园失物招领平台。核心特性为以图搜图——上传一张物品照片，系统在全部已审核启事中找出"同一件东西"的其它照片，不依赖文字描述，也不要求用户手写标签。

**配套能力**：发布与审核流转（待审核 → 通过上墙）、认领申请与发布者审核、站内消息与私信、守望订阅（搜不到时挂照片等推送）、管理后台（看板/审核/用户/日志/运维）、认领证明 PDF 交付。

**范围边界**：单 Web 部署形态（后端同源托管前端）；另提供 Windows 独立安装包作为可选交付（Electron + 内置 JRE + H2，独立于 Web 版构建）。

## 3. 技术可行性

### 3.1 候选方案对比（核心检索）

| 方案 | 原理 | 优点 | 缺点（课程环境下） | 结论 |
|---|---|---|---|---|
| A. 文字标签检索 | 用户手写标签 + LIKE 匹配 | 实现最简单 | 标签质量不可控，"卡包≠钱包"问题无解；市面方案同质化 | 否决 |
| B. 深度学习特征检索 | CNN/CLIP 向量 + 相似度 | 精度上限高 | 需要模型推理与向量库（Milvus/Faiss），部署重、资源消耗大，超出课程环境承载力 | 否决 |
| **C. 感知哈希 pHash** | 64 位指纹 + 汉明距离 | **零额外基础设施**：指纹就是一个 BIGINT 列，检索是一条 SQL；对缩放/亮度/对比度鲁棒 | 对大角度旋转不鲁棒（算法边界，已量化） | **采纳** |

### 3.2 算法可行性（已用实验证实，非纸面推断）

方案 C 的效果不是预估，而是**实测结论**（详见《11-以图搜图准确率实验报告》）：

| 指标 | 实测值 | 说明 |
|---|---|---|
| 召回率 | **48/56 = 85.7%** | 56 个查询变体（缩放/裁剪/亮度/对比度/灰度） |
| 误检 | **0** | 阈值 12 过滤后无一例跨物品误报 |
| 单张检索耗时 | **约 54 ms**（41~54 ms） | 含上传与 pHash 计算，远低于 2s 的 NFR 指标 |
| 并发 | 20 并发全部成功，总耗时 132 ms | 结果一致 |
| 算法横评 | pHash 全面优于 aHash / dHash | 同一实验框架下三算法对比 |

阈值 12 与 Top-10 由网格扫描标定（`src/web-lostfond/backend/scripts/eval_recall.py --grid`），而非拍脑袋取值。

### 3.3 技术栈成熟度

全部采用主流、文档齐全、社区活跃的技术：Spring Boot 3.3.5 / MyBatis-Plus 3.5.7 / JJWT 0.12.6 / JImageHash 1.0.0（Maven Central）/ Vue 3.5 / Vite 6 / Element Plus / ECharts 6 / MySQL 8+。pHash 核心依赖 JImageHash 是现成开源库，无需自研图像算法。

### 3.4 团队能力
小组 5 人，按课件六类岗位分工（项目经理 / 分析设计 / 后端编码 / 前端编码 / 测试 + 数据库兼岗，见 `other/other/Creator/过程资料/选题/失物招领平台-五人分工方案.md`）；全员已修完 Java 与数据库课程，选题前的 GitHub 参考项目调研为架构与表设计提供了可对照的样板。

### 3.5 结论
技术可行。核心算法风险已通过原型实验在编码前消除（先实验、后立项编码的顺序保证了这一点）。

## 5. 操作可行性

- **用户侧零学习成本**：核心操作就是"拍照 → 上传"，不需要填标签、不需要学检索语法；发布、认领、消息均为常规 Web 交互，与主流网站习惯一致。
- **管理侧轻量**：管理员只需审核（通过/驳回）、下架、封禁三类操作，看板自动汇总；审核结果自动通知发布者，无需人工转达。
- **部署侧一条命令**：`mvn spring-boot:run` 启动即自动建播种数据（60 启事 + 图片 + pHash 全部重算），演示环境一键重建；Windows 桌面版双击安装包即用（内置 JRE 与 H2，免装 MySQL）。
- **维护侧可自查**：`scripts/test_api.py` 141 断言幂等自测、管理端 `db-counts` 八表行数自检，非开发人员也能确认系统健康。

## 6. 法律与社会可行性

- **开源许可合规**：所用第三方组件（Spring Boot/Apache-2.0、Vue/MIT、MyBatis-Plus/Apache-2.0、JImageHash 等）均为 MIT / Apache-2.0 类宽松许可，允许学术使用与再分发；项目无商业收费。
- **内容合规**：所有启事经管理员审核后才对外可见/可搜；违规内容可下架并留痕（admin_log）；守望订阅为课程演示功能，不接真实支付。
- **隐私与安全**：口令 BCrypt 加密入库；学号仅用于登录、不对他人公开（他人主页脱敏）；联系方式仅认领审核时对发布者可见；敏感配置（数据库口令、JWT secret）外置于不入库的 `application-local.yml`。
- **社会价值**：提升校园失物找回效率，减少财物损失；"守望订阅"把"这次没搜到"变成"后续有人捡到主动告诉你"，符合失物招领的真实使用节奏。
