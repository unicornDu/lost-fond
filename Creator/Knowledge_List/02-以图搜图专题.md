## 1. 为什么普通哈希不行

| 哈希 | 特性 | 能否用于比相似 |
|---|---|---|
| MD5 / SHA-256 | **雪崩效应**：改一个字节，结果面目全非 | ❌ 无法比较相似度 |
| aHash / dHash / **pHash** | **感知哈希**：从图像结构提取特征，视觉相似 → 指纹相近 | ✅ 比"相差多少位" |

## 2. pHash 计算五步（★必背，能边画边讲）

```
原图
 ① 灰度化          → 去掉颜色干扰（颜色不该影响"是不是同一个东西"）
 ② 缩放到 32×32     → 去掉尺寸/分辨率差异，只留结构
 ③ DCT 离散余弦变换  → 像素域 → 频率域
 ④ 取左上 8×8 低频   → 低频 = 画面整体轮廓；丢弃高频（纹理/噪点）
 ⑤ 按均值二值化      → 每个低频系数 > 全体系数均值 记 1，否则 0 → 64 位指纹
```

- 结果：一个 **64 位**二进制数，存成 Java `long` / MySQL `BIGINT`。
- 第 ④ 步为什么取左上：DCT 后**低频集中在左上角**（图像能量主要落在低频），所以左上 8×8 就是"最能代表长相"的部分。
- 第 ⑤ 步为什么用**均值**：用相对阈值而非绝对阈值 → 整体变亮/变暗时所有系数同比上升，仍大于均值 → **因此抗亮度变化**。

代码：`backend/.../util/PHashUtil.java`，底层 `dev.brachtendorf.jimagehash.hashAlgorithms.PerceptiveHash`。

- [ ] 能画出五步并说出每步"去掉/保留了什么"
- [ ] 被问"为什么缩到 32×32 却只取 8×8"时能答：32×32 是为了让 DCT 有足够分辨率，取左上 8×8 是取低频、降维到 64 位

## 3. 汉明距离与相似度

```java
// PHashUtil
public int hammingDistance(long a, long b) { return Long.bitCount(a ^ b); }
public double similarity(long a, long b)   { return round1((1.0 - dist / 64.0) * 100); }
```

| 概念 | 定义 | 本项目实现 |
|---|---|---|
| 汉明距离 | 两个等长二进制串**对应位不同的个数** | `Long.bitCount(a ^ b)` |
| 相似度 | `(1 - 距离 / 64) × 100%`，保留 1 位小数 | 距离 0 → 100%；距离 10 → 84.4%；**距离 12 → 81.3%** |
| 判定相似 | 距离 ≤ 阈值（**12**） | `HAVING dist <= 12` |

> 交叉验证：阈值 12 ⇒ 相似度下限 81.25% ⇒ 报告里每张查询图的"最低相似度"都 ≥ 81.3%（除个别族内分化），数字自洽，**这是老师可能抽查的点**。

- [ ] 能手算：距离 8 的相似度 = (1-8/64)×100 = 87.5%
- [ ] 能解释"为什么存 BIGINT 而不是字符串/64 个布尔"（省空间 + 可直接按位运算，`^` 和 `BIT_COUNT` 都在库内完成）

## 4. 核心 SQL（★★★ 必背，逐行能讲）

`backend/.../mapper/ItemImageMapper.java#searchByHash`

```sql
SELECT ii.item_id AS itemId, MIN(BIT_COUNT(ii.phash ^ #{q})) AS dist
FROM item_image ii
JOIN item i ON i.id = ii.item_id
WHERE ii.phash IS NOT NULL
  AND i.audit_status = 1                    -- 只搜审核通过的
  AND i.status NOT IN ('已下架','已关闭')     -- 排除下架/关闭
GROUP BY ii.item_id
HAVING dist <= #{threshold}                 -- 阈值过滤（12）
ORDER BY dist ASC                           -- 最像的排前面
LIMIT #{limit}                              -- Top-N（10）
```

| 片段 | 作用 | 为什么 |
|---|---|---|
| `phash ^ #{q}` | **按位异或**：相同位得 0、不同位得 1 | 汉明距离的前提 |
| `BIT_COUNT(...)` | 数 1 的个数 = 不同位数 | MySQL 内置位函数，库内算完不用回传 Java |
| `MIN(...) + GROUP BY item_id` | 一条启事可能多图，取**最像的那张**的距离 | 同物多拍，命中面更大 |
| `JOIN item` | 把审核/下架过滤**下推进 SQL** | 见坑 ② |
| `HAVING` 而非 `WHERE` | 过滤的是聚合结果 `dist` | 聚合别名只能用在 HAVING |
| `LIMIT` 最后 | 截断 Top-N | 顺序必须是"先过滤再截断" |

### 坑 ①：`XOR` ≠ `^`（MySQL 语义陷阱）

- `^` 是**按位异或**，`XOR` 是**逻辑异或**（只返回 0/1）。
- 误用 `XOR` ⇒ 几乎所有距离都是 0 或 1 ⇒ **相似度全 100%**。
- 项目里踩过并修复（缺陷 #1）。老师问"怎么算距离"务必答 `^` + `BIT_COUNT`。

### 坑 ②：过滤与 LIMIT 的顺序（逻辑缺陷）

- 曾经的实现：SQL 只按距离取 Top-N，再在 Java 侧过滤待审/下架。
- 后果：**待审核条目占满了 Top-N 名额**，用户看到的结果比实际少（被截断）。
- 修复：过滤条件下推进 SQL，先过滤再 `LIMIT`。
- 这体现的思路：**"过滤在前、分页/截断在后"，任何列表接口都适用。**

- [ ] 能默写这条 SQL
- [ ] 能讲清两个坑各自的症状、根因、修法
- [ ] 被问"为什么 WHERE 里不写 dist <= 12"时能答：dist 是聚合后的别名，WHERE 阶段还没算出来

## 5. 阈值 12 / Top-10 是怎么定的（★实验出处）

### 5.1 两套协议，别混用（重要）

| 协议 | 数据 | 回答的问题 | 出处在报告 11 |
|---|---|---|---|
| A 受控变体库 | 6 个对象、1 张 ref 建索引、72 张变换查询 | 算法**对变换的鲁棒性** | §2.1 / §2.2 |
| B 真实种子库 | 60 启事 / 120 图 / 56 条过审候选 / 6 张留出查询图 | 用户**实际搜不搜得到** | §2.4 |

> 两套数字**不可互推**。答辩若被追问，先说明"这是哪套协议下的数字"，这本身是加分项。

### 5.2 端到端网格扫描（协议 B）

| top-n | th=8 | th=10 | th=12 | th=14 | th=16 |
|---|---|---|---|---|---|
| 6 | 42.9% / 0 | 53.6% / 0 | 60.7% / 0 | 60.7% / 0 | 64.3% / 0 |
| 10 | 50.0% / 0 | 67.9% / 0 | **85.7% / 0** | 89.3% / 0 | 96.4% / 0 |
| 20/50 | 50.0% / 0 | 67.9% / 0 | 85.7% / 0 | 89.3% / 0 | 96.4% / 0 |

（格式：召回 / 误检数；top-n ≥ 10 后三行完全相同 → 证明旧 top-n=6 是**截断瓶颈**）

### 5.3 结论与理由（背这段）

- **为什么 top-n 从 6 改到 10**：top-n=6 时召回只有 53.6%~60.7%，扩大后同阈值下 85.7% —— 说明瓶颈不是算法而是**返回条数截断**。
- **为什么阈值取 12 而不是 14/16**：
  1. 14/16 召回升到 89.3%/96.4%，但已贴近**跨物体误检**风险区（协议 A 的 strong 组在 t≥12 出现 Precision<Recall 分化）；
  2. 返回列表变长（平均 8.3 → 9.0 条），用户体验下降；
  3. th=12 同时是协议 A **mild 组 pHash 的 F1 峰值**（0.833），两套协议互证。
- **逐图召回（协议 B，th=12/top-10）**：

| 查询图 | 命中/候选 | 召回 | 最低相似度 |
|---|---|---|---|
| q-cup | 8/8 | 100% | 81.3% |
| q-keys | 8/8 | 100% | 82.8% |
| q-earbuds | 10/10 | 100% | 85.9% |
| q-umbrella | 10/10 | 100% | 81.3% |
| q-scarf | 8/10 | 80% | 89.1% |
| q-card | 4/10 | 40% | 100% |
| **合计** | **48/56** | **85.7%** | 误检 0 |

- **q-card 只有 40% 怎么解释**：卡套反光变体的汉明距离普遍 >12；命中的那些相似度都是 100%，是"**族内全对或全不对**"的分化 —— 属 pHash 能力边界（反光/裁剪），**不为单张图妥协阈值**。

- [ ] 能解释 q-card 的 40% 而不是含糊说"效果一般"

## 6. 能力边界（诚实是加分项）

| 变换 | 鲁棒？ | 实测（@t=10） | 原因 |
|---|---|---|---|
| 亮度 / 对比度 | ✅ | pHash 1.00 | 均值二值化抵消整体明暗 |
| 灰度 + 模糊 | ✅ | 1.00 | 本就先灰度、只看低频 |
| 缩放 | ✅ | 1.00（dHash 只有 0.67） | 第②步统一缩到 32×32 |
| JPEG q30 / 模糊 2px / 亮度 1.3 / 缩放 50% | ✅ | 1.00 ×4 | 低频结构不变 |
| **旋转 5° / 10°** | ❌ | 0.33 / **0.00** | DCT 对方向敏感，旋转打乱低频布局 |
| **裁剪 85% / 70%** | ❌ | 0.00 / **0.00** | 构图比例变了，结构不再是原结构 |

**关键结论**：裁剪 70% 时**三种哈希全部归零** → 这是**感知哈希家族的共性局限，不是选型问题**。这句话一定要会说，否则会被认为"选错了算法"。

**系统层面的缓解（已实现，答这三点）**：
1. 发布时支持 **1~3 张不同构图**上传 → 一条启事多个指纹，提高命中面（种子数据就是"同物多拍"）；
2. 前端拍摄引导"拍清特征、拍满物品"；
3. 演示素材**故意只用鲁棒变换**生成，不用旋转（`gen_seed_images.py` 注释有说明）。

- [ ] 能说出"哪些变换稳、哪些不稳"并给出实测数字
- [ ] 被问"旋转怎么办"时，先承认局限，再给三条缓解 + 一条未来方向（旋转不变特征 / 多角度入库）

## 7. 三种感知哈希对比（含诚实结论）

| 算法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| aHash | 缩 8×8 按均值二值化 | 最快、最简单 | 抗亮度/构图差，区分度低 |
| dHash | 相邻像素**梯度**比较 | 比 aHash 稳 | 仍偏简单；缩放即掉到 0.67 |
| **pHash** | DCT 取低频 | 抗压缩/缩放/亮度最好 | 多一次 DCT 计算 |

### 老师可能挖的坑："你的表里 aHash 分数比 pHash 高，为什么还选 pHash？"

这是**真实数据**，不要回避。正确答法：

> "在 6 个对象的小库上，aHash 的 F1 确实略高（mild t=10：0.867 vs 0.800）。但它的宽容是**用区分度换来的**——阈值升到 12 时 aHash 出现 Precision(0.798) < Recall(0.810) 的**跨物体误检分化**，库越大误检越多；而 pHash 在缩放/压缩场景稳定 100%、误检最少，与文献共识一致。所以我们维持 pHash，同时**诚实承认本实验规模（6 对象/72 查询）不足以给出统计显著结论**。"

> 这段话在原报告 §3.2 有明确记载，属于项目自己做的复盘（05 D-01），照实说即可。

## 8. 性能与扩展

| 场景 | 实测 | 条件 |
|---|---|---|
| 单次搜图 | min 35 / **avg 40** / max 46 ms | 120 张索引图，th=10/top-n=6（旧参数） |
| 单次搜图（现行） | **41~54 ms** | th=12/top-n=10，两轮复测 |
| 20 并发 | 总 **132ms**，全部成功、结果一致 | 同环境 |
| 指标要求 | < 2s（NFR-1） | 余量充足 |

**为什么现在不做索引优化**：数据量千级以内，`item_image` 全表 `BIT_COUNT` 扫描已在几十毫秒量级；`phash` 上建普通 B-Tree 索引对**范围扫描**（`<=` 汉明距离）无效，反而增加写入成本 —— 这是数据库设计文档里写明的**主动取舍**。

**规模化方案（被问"一万张图怎么办"时答）**：
1. 分段哈希 + 前缀索引粗筛（64 位拆 4×16 位，先按前缀缩小候选）；
2. 倒排 / BKD 树多列索引；
3. 内存向量库（如改成 CNN 特征向量 + ANN 近似最近邻）；
4. 前置缓存（热门查询结果缓存）。

## 9. 工程落地细节（这些细节最能体现实做过）

| 细节 | 做法 | 为什么 |
|---|---|---|
| 发布时算哈希 | `ItemService.publish` 遍历每张图 `getBytes()` → 落盘 → `PHashUtil.hash(bytes)` → 存 `item_image.phash` | 写入时一次算好，查询时零计算 |
| 字节流只能读一次 | **先 `getBytes()` 再既写盘又算哈希** | 曾经先 `transferTo` 落盘再 `getBytes()`，流已被消费导致算哈希失败（缺陷记录） |
| 补算入口 | `POST /api/search/reindex`，后台「运维工具」也有按钮 | 历史数据/漏算时可修 |
| 已索引计数 | `GET /api/search/indexed-count` | 演示时先证明"库里有指纹" |
| 封面图 | 第一张图设为 `cover_img` | 列表页只加载一张小图 |
| 缩略图 | 480px 宽 `_thumb` 文件 | 列表省流量，可由后台批量重建 |
