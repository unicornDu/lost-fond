## 1. 八表总览与关系（★能画）

```
user ──1:N──> item ──1:N──> item_image (含 phash ★)
 │              │
 │              ├──1:N──> claim_record <──N:1── user (申请人)
 │              └──1:N──> delivery (认领证明 / 报表 / 匹配报告)
 ├──1:N──> message
 ├──1:N──> admin_log
 └──1:N──> favorite (收藏)
```

| 表 | 存什么 | 关键点 |
|---|---|---|
| `user` | 账号 | `account`（学号）唯一；`password` 存 BCrypt 密文；`role` 0/1；`status` 1 正常 0 封禁 |
| `item` | 启事 | `type`=lost/found；`status` 业务状态；`audit_status` 0 待审 / 1 通过 / 2 驳回（**两个状态字段，别混**） |
| `item_image` | 启事图片 | **`phash BIGINT`** 64 位指纹，以图搜图的根 |
| `claim_record` | 认领申请 | `proof` 认领凭证；`status` 审核中/已通过/已拒绝 |
| `message` | 站内通知 | `is_read`、`ref_id` 指回业务对象 |
| `admin_log` | 管理操作审计 | 谁、对什么、做了什么、详情 |
| `favorite` | 收藏 | 唯一键 `(user_id, item_id)`，重复收藏幂等 |
| `delivery` | 可下载交付物 | `biz_type`：CLAIM_CERT / REPORT_CSV / MATCH_REPORT |

## 2. 关键表字段（答辩抽查概率最高）

**item**

| 字段 | 说明 |
|---|---|
| `type` | `lost` 寻物 / `found` 招领 |
| `status` | 寻找中 / 待认领 / 认领申请中 / 已找回 / 已认领 / 已下架 / 已关闭 |

**item_image**

| 字段 | 说明 |
|---|---|
| `img_url` | 相对路径 `/uploads/yyyy/MM/uuid.jpg` |
| `phash` | **BIGINT**，64 位指纹；为 NULL 表示未算（需 reindex） |

## 3. 索引与取舍（★这是最能体现思考的部分）

| 索引 | 为什么建 |
|---|---|
| `item.idx_type_status(type, status)` | 墙页最常用：按类型 + 状态过滤 → 联合索引命中 |
| `item.idx_category` | 分类筛选 |
| `item.idx_user` | "我的发布" |
| `item.idx_create_time` | 按时间排序/分页 |
| `item_image.idx_phash(phash)` | 方便定位"哪些图已算指纹"，也服务 reindex |
| `user.uk_account` | 唯一索引，防重复注册 |

### 两个"故意不做"（被问就是加分点）

**① 为什么不给 `phash` 建前缀/哈希索引来加速搜图？**

> 搜图条件是 `BIT_COUNT(phash ^ q) <= 12`，这是**按位异或后的计数**，不是范围比较也不是等值比较，**B-Tree / 哈希索引都用不上**；强行建索引只增加写入成本。当前千级数据量全表扫几十毫秒即可，等万级再考虑分段哈希前缀粗筛或改用向量库。

**② 为什么不做全文索引（`FULLTEXT` / ngram）？**

> 当前关键词搜索用 `LIKE '%k%'`，在千级数据量下足够快；ngram 全文索引需要额外配置分词、维护倒排、对中文还要调 `ngram_token_size`，**维护成本高、收益小**，作为扩展项写进设计文档。

## 4. 物品状态机（M5 核心，★成员B 必画）

```
发布(lost)  → 寻找中          发布(found) → 待认领
      │                            │
      └──── 有人申请认领 ──────────┘
                    ↓
              认领申请中
              ↙        ↘
    发布者通过          发布者拒绝
        ↓                  ↓
已找回(lost)/已认领(found)   回退 寻找中/待认领
        │                  （仅当没有其他"审核中"申请）
        ↓
   自动关闭同 item 其余"审核中"申请 → 置已拒绝 + 通知

任意状态 ──管理员──> 已下架 / 已关闭
```

**三条设计要点（必答）**：

1. **为什么认领要发布者确认**：防冒领。申请人必须写"只有失主才知道的特征"（`proof`），发布者人工核对。
2. **并发申请怎么办（竞争状态机）**：
   - 通过 A 的申请时，**自动把同 item 其余"审核中"置为已拒绝**并逐个通知 → 不可能"两人同时认领成功"。
   - 拒绝某条时，**只有当没有其他"审核中"申请**才把物品回退到 寻找中/待认领；否则保持"认领申请中"。
3. **状态白名单守卫**：只有 寻找中 / 待认领 状态才能发起认领；重复申请被拒（同 item + 同申请人已有"审核中"）。

- [ ] 能画出状态机全部箭头（含"拒绝时是否回退"的条件）
- [ ] 能说清并发两人认领的处理，并举出"自动关闭其余申请"这条

## 5. 为什么 pHash 存 BIGINT

| 方案 | 空间 | 可比较 | 结论 |
|---|---|---|---|
| 64 个布尔/字符 | 大 | 需逐位比 | ❌ |
| 64 位字符串（"1010…"） | 64 字节 | 需 Java 侧解析 | ❌ |
| **BIGINT / Java long** | 8 字节 | 库内 `^` + `BIT_COUNT` 直接算 | ✅ |

- 64 位正好等于 MySQL `BIGINT` / Java `long` 的宽度。
- 有符号不影响按位运算：`^` 与 `BIT_COUNT` 都是按位语义，符号位一视同仁。

## 6. delivery 表：受控交付设计（P1 亮点）

**问题**：认领证明 PDF、统计报表 CSV、匹配报告 PDF 这类"生成出来的文件"，怎么给用户而不把文件路径暴露出去？

**做法（记住这句）**：**业务只往 `delivery` 表声明"要交付什么"，前端只拿 `deliveryId`，从不拼路径。**

| 字段 | 作用 |
|---|---|
| `owner_id` | 归属人（越权校验用） |
| `biz_type` | CLAIM_CERT / REPORT_CSV / MATCH_REPORT |
| `biz_id` | 关联启事/认领（报表可空） |
| `file_path` | 相对 deliveries 根目录的路径（**绝对路径不出库**） |
| `content_type` / `size` / `status` | 下载头与状态 |

**下载链路**：`GET /api/file/download?id=` → 校验 `owner_id` 与角色 → 读盘 → 响应带 `no-store`、`nosniff`、CSP、UTF-8 文件名。
**下载**：`/api/file/download` 读字节流回传（no-store/nosniff/CSP 三件套），**渲染层全程不接触文件系统**。

- [ ] 能说出交付下载为什么要走受控路由而不是直接暴露磁盘路径

## 7. 事务边界（@Transactional 用在哪）

| 场景 | 一个事务里包含 | 为什么必须原子 |
|---|---|---|
| 发布启事 | `insert item` + 多条 `insert item_image` | 只成功一半会出现"有启事没图"（无法搜图、列表空白） |
| 认领审核通过 | `update claim` + `update item` + `insert message` + `insert delivery` | 状态与通知不一致会出现"显示已认领但对方没收到凭证" |
| 收藏 | `insert favorite`（唯一键保证幂等） | 重复点击不报错 |

**例外处理**：认领证明 PDF 生成失败**只记日志、不回滚审核** —— 主流程（认领成功）不能被附件生成拖垮，这是有意识的取舍，答辩可主动提。

## 9. 高频追问

| 问 | 答 |
|---|---|
| 为什么图片不存数据库 BLOB？ | 撑库、备份臃肿、无法走静态资源/CDN；存路径 + 指纹更灵活 |
| 八张表够吗？ | 课程范围内覆盖用户/内容/关系/通知/审计/交付六类语义；扩展可加 tag、report（举报）等 |

| 怎么保证学号不重复？ | `user.account` 唯一索引 + 注册前 `selectCount` 查重（双保险，唯一索引才是最终防线） |
