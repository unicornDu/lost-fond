### 1.3 以图搜图准确率实验报告（负责人：成员E，核心加分项）
- 【现状】`image-search.hamming-threshold: 10` 是配置直给、无实验依据；后端只算了 pHash，没有 aHash/dHash 可对比。
- 【**方法论问题（必须先解决，否则实验结论不可信）**】现有 44 张种子图看似"同物多拍"，实际只有 5 种**轻微**变换（resize / 居中裁剪 / 亮度 / 对比度 / 灰度+轻微模糊），且同一"物"的两张图来自同一张底图。在这种近重复样本上，aHash/dHash/pHash 都会接近满分，**实验表会"太漂亮"反而不可信**；同时只有 4 张留出查询图，**没有负样本，画不出 P/R 曲线**。
- 【做法】
  1. `PHashUtil` 增加 aHash/dHash（JImageHash 原生支持 `AverageHash` / `DifferenceHash`）；
  2. **先把种子图做强（依赖 2.12）**：每物至少 5 张真实变体，引入**旋转**（±5°/±10°）、**换背景/换拍摄距离**、**低质量 JPEG 重压缩（q=30）**、**不同裁剪比例**、**运动模糊**；
  3. **构造带标注的查询集**：正样本 = 同物变体；**负样本 = 同类别不同物**（如"另一个保温杯""另一副白耳机"）——这是老师最容易追问的点；
  4. 在阈值 4/6/8/10/12 下统计三种哈希的 Precision / Recall / F1，出对比表 + 曲线图（含"阈值—误报率/漏报率"权衡图）；
  5. 结论回填 `application.yml` 的 `hamming-threshold`，并在报告中说明"为什么最终选 X"。
- 【验收】docs/ 新增 `11-以图搜图准确率实验报告`：含**正负样本集说明**、数据表、曲线图；阈值有实验出处且与 `application.yml` 一致。

### 2.6 认领状态机漏洞（P0，含「拒绝」路径实测复现）
- 【现状·通过路径】通过 A 后，B/C 的申请仍"审核中"且无通知；且 `audit()` 不校验物品是否已认领，发布者可再通过 B，产生两条"已通过"。
- 【现状·拒绝路径（实测复现）】拒绝分支第 83 行**无条件**把物品状态改回 `寻找中/待认领`，不管同物品是否还有其他"审核中"申请——A 发布 → B、C 申请 → 拒绝 B → 物品显示"寻找中"但 C 的申请还挂着，状态机自相矛盾。
- 【现状·申请入口守卫过窄】`apply()` 只挡"已认领/已找回"，**已下架/已关闭的启事仍可被申请**。
- 【做法】
  1. `audit()` 开头加物品状态守卫（已认领/已找回直接拒）；
  2. 通过某申请时，同物品其余"审核中"申请批量置"已拒绝"并逐个推消息；
  3. ★ **拒绝时，仅当同物品已无其他"审核中"申请才回退物品状态**；
  4. `apply()` 守卫改白名单：仅 `寻找中` / `待认领` 可申请。
- 【验收】一物多申请：通过一人其余自动关闭并通知；拒绝其一后物品仍为「认领申请中」；重复审核被拦截；已下架不可申请。完整代码见附录 D3/D4。

### 2.27 发布与认领的三处前端隐患（P1）
- 【现状】① `el-date-picker` 无 `value-format`，靠手写 `fmtTime()` 拼时间 → 类型/时区漂移；② 防重复提交只靠 `:loading`（EP 的 loading 不阻止点击），连点发两个 POST（后端无幂等键），认领提交同病；`PublishView` 还有一段永远进不去的死代码 `if (!user.info)`；③ 上传无体积校验，手机原图 10MB+ 撞 20s 超时。
- 【做法】① `value-format="YYYY-MM-DD HH:mm:ss"` 并删 `fmtTime()`；② 提交函数首行 `if (submitting.value) return` 或改 `:disabled`，删死代码；③ `beforeUpload` 校验 ≤5MB + 上传进度条。

### 2.28 `ItemForm` 缺长度校验 + 后端静默兜底（P1）
- 【现状】`ItemForm` 仅 type/title 有 `@NotBlank`、无任何 `@Size`；DB 列宽 title(60)/category(20)/location(50)/description(500)，超长抛 `DataIntegrityViolationException` → 兜底返回 `"服务器开小差了：" + e.getMessage()`（泄露 SQL，即 2.24）。另有两处静默污染：`parseTime()` 非法日期静默改当前时间；`type` 非法值静默变 lost。
- 【做法】① `ItemForm` 补 `@Size(max=60/20/50/500)`，`type` 加 `@Pattern("^(lost|found)$")`；② 时间解析失败抛 `BusinessException("时间格式不正确")`；③ `GlobalExceptionHandler` 增加 `DataIntegrityViolationException`/`HttpMessageNotReadableException` 处理器返回友好 400。
- 【验收】100 字标题被 400 拦下；`type=hack`、`happenTime=abc` 被拒；不再出现 500 兜底文案。

### 2.29 认证纵深：登录限流、登出吊销、`admin_log` 读取入口（P1）
- 【现状】① `/api/auth/login` 无失败限制可无限爆破；② 无 logout/令牌吊销，前端登出只清 localStorage，令牌 7 天内始终有效；③ `admin_log` 唯一用法是 insert，七个管理动作都留痕但谁也看不到。
- 【做法】① 登录失败计数（内存 `ConcurrentHashMap<账号, 次数+锁定时间>`，5 次锁 10 分钟即可，无需 Redis）；② 报告写明"JWT 无状态、无服务端登出"的取舍，或加 `token_version` 轻量吊销；③ ★ 最省力且加分：2.9 后台加"操作日志"页，`GET /api/admin/logs` 分页读表（附录 E4）。
- 【验收】连错 5 次密码被锁定；后台能翻看操作日志。

### 2.30 首页统计口径错误 + 落地页硬编码假数据（P1，防穿帮）
- 【现状】① `homeStats` 的 lostCount 无 status 过滤，把"已找回"算进"寻找中"（实测 lostCount=13，实际在找的只有 11）；② `WelcomeView` 整页写死"1,286 名同学/128 件/98.2%"，而首页真实 stats 是 `reunited:4 / lost:13 / found:9`（用户 19）——答辩时对照即穿帮。
- 【做法】① lost/found 计数加 `status NOT IN ('已找回','已认领')`（或语义改"累计"并在标签写清）；② 落地页数字接 `api.stats()`，接不了的改定性文案或标注"示意数据"。
- 【验收】落地页与首页数字一致；"寻找中"计数与墙上条数对得上。

### 2.31 前端健壮性包（P1–P2）
- 【现状】
  - **读取接口失败全部静默**：HomeView/WallView/ProfileView/DetailView 只 `console.error`，用户无法区分"没数据"和"后端挂了"；
  - **内存泄漏**：`SearchImageView` 的 `URL.createObjectURL` 从不 revoke；GooeyNav 粒子 `setTimeout` 未登记清理，卸载后仍操作 DOM（一次点击最多 15 个悬挂定时器）；
  - **请求竞态**：`WallView` 的 watch 连发两次；`DetailView` 切启事不取消旧请求 → 快速点击出现"标题 A 描述 B"；
  - **空值无保护**：`ItemCard` 直接 `item.time.slice(5,16)`，而 `views` 可空 Integer；
  - **分页参数无上限**：`?size=100000` 可全量拉取，`page=-1`、`size=0` 不报错。
- 【做法】① 四处 catch 补 `ElMessage.error` + error 态 + 重试按钮；② revoke 与定时器统一清理；③ 自增 `reqSeq` 只接受最新响应（或 AbortController）；④ 统一空值工具函数；⑤ 后端对 `size` 设上限（`Math.min(size,100)`）并校验 `page>=1`。
- 【验收】停掉后端有明确错误提示与重试；反复操作无内存增长；`size=100000` 被截断。

### 2.32 `views` 非原子自增 + `idx_phash` 无效索引（P2，报告素材）
- 【现状】① `detail()` 是"读出来 +1 写回"，并发丢更新，且 GET 写库不幂等；② `idx_phash` 对 `BIT_COUNT(phash ^ ?)` 永远无效（EXPLAIN 证实未选中）。
- 【做法】① 改 `UPDATE item SET views = views + 1 WHERE id = ?`；② 删除 `idx_phash` 或注明"为未来分段前缀索引预留"——写进报告"索引设计"一节是很好的加分点。
- 【验收】报告有索引取舍说明；并发刷新不丢计数。

### 2.39 前端启动时不刷新用户态（P1，v4.0 新增）
- 【现状】`stores/user.js` 写好了 `refresh()`（调 `GET /api/auth/me`），但**全前端零调用**。后果：用户被封禁/降权/改昵称后，前端仍显示 localStorage 里的旧身份（旧昵称、旧角色），与管理端操作脱节；配合 2.24 的封禁实时性是同一块拼图。
- 【做法】`App.vue` 的 `onMounted` 里：`if (userStore.token) userStore.refresh()`（refresh 失败会自动 logout，再被 2.14 的 401 跳转兜底）。
- 【验收】手工改库把某用户 role 清 0 后刷新页面，其"管理员"入口消失。

### 2.40 登录页"记住我"是摆设（P2，v4.0 新增，防穿帮）
- 【现状】`AuthView` 的"记住我"checkbox 只绑了一个从未使用的 ref，不随请求提交；后端 `jwt.expire-minutes: 10080` 固定 7 天——勾不勾没有任何区别。答辩被点到"记住我是干什么的"会穿帮。
- 【做法】二选一：① 实现——登录请求带 `rememberMe`，后端按其区分 TTL（勾选 30 天 / 不勾 1 天）；② 删掉 checkbox。**推荐 ①，改动只有 `LoginReq` 一个字段 + `AuthService` 签发时取 TTL 的一行。**
- 【验收】勾选与不勾选登录后，token 的实际有效期可区分（或 checkbox 已删除）。

### 2.41 数据库备份方案缺失（P1，v4.0 新增，分工交付物）
- 【现状】《五人分工方案》给"数据库及文档人员"定的交付物包含"备份方案"，目前为零——数据库里积累的真实注册用户与发布数据丢了就没了。
- 【做法】`scripts/backup.md` + 一个批处理/Shell 脚本：`mysqldump lost_found > backup/yyyyMMdd.sql` + 打包 `uploads/`（图片是文件系统存储，不在库里）；README 加"每周备份一次 + 演示前备份一次"两句话。
- 【验收】照文档执行一次备份并成功恢复到空库。

### 2.42 部署三连坑（P2，v4.0 新增，并入 1.4 部署手册）
- 【现状】① Knife4j `/doc.html` 与 springdoc 在 8080 公开暴露全量接口清单，演示方便但部署后等于交出接口地图；② `file.upload-dir: ./uploads` 是相对启动目录的路径，`java -jar` 换个目录启动会另建一个空 uploads，图片全部 404；③ README 里 Maven 路径硬编码 `D:\Visual_Stdio_Code\Maven\...`，换机器即失效。

### D4. `audit()` 完整修正（通过路径关竞争 + 拒绝路径条件回退 + 状态守卫）
```java
@Transactional
public void audit(Long claimId, Long publisherId, ClaimAuditReq req) {
    ClaimRecord c = claimMapper.selectById(claimId);
    if (c == null) throw new BusinessException(404, "认领申请不存在");
    Item item = itemMapper.selectById(c.getItemId());
    if (item == null) throw new BusinessException(404, "启事不存在");
    if (!item.getUserId().equals(publisherId)) throw new BusinessException(403, "只有发布者本人可以审核");
    if (!"审核中".equals(c.getStatus())) throw new BusinessException("该申请已处理过");
    // ★ 新增①：物品已完成认领则不再受理
    if ("已认领".equals(item.getStatus()) || "已找回".equals(item.getStatus()))
        throw new BusinessException("该物品已完成认领，申请已关闭");

    boolean lost = "lost".equals(item.getType());

    if (req.isApprove()) {
        c.setStatus("已通过");
        c.setReply(blankTo(req.getReply(), "已通过认领，请联系交接"));
        claimMapper.updateById(c);

        item.setStatus(lost ? "已找回" : "已认领");
        itemMapper.updateById(item);

        // ★ 新增②：关闭同物品其余"审核中"申请并逐个通知
        List<ClaimRecord> others = claimMapper.selectList(new QueryWrapper<ClaimRecord>()
                .eq("item_id", c.getItemId()).eq("status", "审核中").ne("id", c.getId()));
        for (ClaimRecord o : others) {
            o.setStatus("已拒绝");
            o.setReply("物品已被其他申请人认领");
            claimMapper.updateById(o);
            push(o.getClaimantId(), "claim", "认领申请未通过",
                 "你对「" + item.getTitle() + "」的申请未通过：物品已被其他申请人认领。", item.getId());
        }
        push(c.getClaimantId(), "claim", "认领申请已通过",
             "你对「" + item.getTitle() + "」的认领申请已通过：" + c.getReply(), item.getId());

    } else {
        c.setStatus("已拒绝");
        c.setReply(blankTo(req.getReply(), "特征不符，已拒绝"));
        claimMapper.updateById(c);   // ★ 关键：先落库，下面的计数才会排除自身

        // ★ 新增③：仅当已无其他"审核中"申请时才回退物品状态
        Long pending = claimMapper.selectCount(new QueryWrapper<ClaimRecord>()
                .eq("item_id", c.getItemId()).eq("status", "审核中"));
        if (pending == null || pending == 0) {
            item.setStatus(lost ? "寻找中" : "待认领");
            itemMapper.updateById(item);
        }
        push(c.getClaimantId(), "claim", "认领申请未通过",
             "你对「" + item.getTitle() + "」的认领申请未通过：" + c.getReply(), item.getId());
    }
}
```
（`ClaimAuditReq.approve` 为 primitive `boolean`，Lombok 生成 `isApprove()`，片段可直接使用。）
