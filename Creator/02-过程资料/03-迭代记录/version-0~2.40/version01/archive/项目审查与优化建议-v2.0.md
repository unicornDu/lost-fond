## 二、代码层面问题（按 P0 / P1 / P2 排序）

### ========== P0：功能断点与防翻车项 ==========

### 2.1 建 git 仓库（P0，半小时，防翻车）
- 【现状】项目无版本控制，误删无法回退；"Git 分支规范"本身是项目经理交付物。
- 【做法】二选一：① 在 `lost-found/` 下 `git init`（推荐，代码与 docs 都在仓内，`Github/`、`Prompt/` 参考资料不进仓）；② 若希望参考资料也留痕，在"软件工程"根目录建仓。创建 `.gitignore`（内容见附录 A），首次提交后建立 main/dev 分支规范。
- 【验收】`git log` 有初始提交；`node_modules/target/dist/uploads 运行时图片/_*.log` 不入仓。

### 2.2 敏感信息外置（P0，建仓前必须做，否则进 git 历史）
- 【现状】`application.yml` 中 JWT secret 硬编码（注释自带 please-change-in-prod）、MySQL root/123456 明文。
- 【做法】新建 `application-local.yml`（gitignore）放真实密码与 secret，`application.yml` 留占位符 `${DB_PASSWORD:123456}` / `${JWT_SECRET:dev-only}`；README 写明本地启动方式。
- 【验收】仓库中 grep 不到真实密码与完整 secret。

### 2.3 认领审核是"盲审"，防冒领主线走不通（P0，v2.0 新增）
- 【现状】申请人提交的 `proof`（认领凭证）和 `contact`（联系方式）已存库，但：
  - `ClaimVO` 只有 `claimId/title/img/location/time/claimStatus/reply`，**没有 proof、contact、申请人昵称/学号**；`ClaimService.build()` 也未组装；
  - 前端 `ProfileView`"收到的申请"中，发布者只能看到物品名和状态，**看不到任何凭证就只能凭感觉点通过/拒绝**；
  - `DetailView` 认领弹窗只有凭证文本框，**没有联系方式输入框**，`ClaimReq.contact` 从未被前端赋值。
- 【做法】
 1. `ClaimVO` 增加 `claimantName / claimantAccount / contact / proof`；
 2. `ClaimService.build()` 批量查申请人信息回填（参考 `ItemService.loadNicknames` 的批量查法）；
 3. 前端"收到的申请"卡片展示申请人、凭证全文、联系方式，再放通过/拒绝按钮；
 4. 认领弹窗加"联系方式（选填）"输入项并随 `applyClaim` 一起提交。
- 【验收】发布者能看到"谁申请、凭证是什么、怎么联系"再审核——这是演示视频"在线认领"故事线的必要镜头。代码片段见附录 D。

### 2.4 站内消息前端整体缺失 + "私信"是假按钮（P0，v2.0 新增）
- 【现状】后端 `GET /api/user/messages`、`/user/messages/unread`、`POST /user/messages/read-all` 三个接口齐全，M5 申请/通过/拒绝各节点都会写消息；但前端**零调用**（api 层只封了前两个，`read-all` 未封装）；`DetailView.vue` 的"私信"按钮是 `ElMessage.info('已发送站内消息（演示）')` 纯占位，演示时一点就穿帮。
- 【做法】
 1. `api/index.js` 补 `readAll: () => http.post('/user/messages/read-all')`；
 2. NavBar 加消息铃铛（进入页面时调 `unread`，未读数 > 0 显示红点）；
 3. 个人中心新增"消息通知"tab：`messages` 列表展示，打开即调 `readAll` 清红点；
 4. 演示前把"私信"假按钮要么接真（可复用消息接口，type=system），要么先删除。
- 【验收】审核通过/拒绝后，申请人侧出现未读消息，点开后红点消失；页面上无"演示"字样的假按钮。

### 2.5 认领状态机并发漏洞（P0，v2.0 新增）
- 【现状】同一物品可被多人申请；通过 A 后，B、C 的申请仍停留"审核中"且收不到通知；更严重的是 `ClaimService.audit()` 只校验申请自身状态、**不校验物品是否已认领**，发布者回头还能再通过 B，产生两条"已通过"记录。
- 【做法】
 1. `audit()` 开头校验物品状态必须为"认领申请中"，否则抛"该物品已完成认领"；
 2. 通过某申请时，把同物品其余"审核中"申请批量置为"已拒绝"，回复"物品已被其他申请人认领"，并为每人推一条站内消息。
- 【验收】一物多申请：通过一人后，其余申请自动关闭且申请人收到通知；重复审核被拦截。代码片段见附录 D。

### 2.6 管理后台接口契约补丁：字段与看板数据不齐（P0，2.7 的前置，v2.0 新增）
- 【现状】直接做后台页面会发现数据不够：
  - `UserVO` 没有 `status`、`createTime` → 用户列表无法显示封禁状态、无法回显按钮；
  - `ItemVO` 没有 `auditStatus` → 审核列表无法区分待审/已通过/已驳回（现在只能靠"已关闭"间接猜）；
  - `AdminService.dashboard()` 只返回 total/reunited/successRate/categoryRatio，**没有用户总数、没有按时间的发布趋势**，看板上的"用户/启事趋势图"无接口可用。
- 【做法】
 1. `UserVO` 补 `status`、`createTime`（字符串），`AdminService.listUsers` 回填；
 2. `ItemVO` 补 `auditStatus`，`ItemService.toVO` 回填；
 3. `ItemMapper` 增加近 7/30 天按日分组统计 SQL，`dashboard()` 返回补 `userCount`、`dailyTrend`。
- 【验收】看板所需数据全部有接口出处，前端不写死任何数据。代码片段见附录 E。

### 2.7 管理后台前端页面（P0，功能最明显的洞）
- 【现状】`AdminController` 六组接口全部就绪且 `UserContext.requireAdmin()` 鉴权完整，但前端**零页面**：无 `/admin` 路由、NavBar 无入口。**开工前先完成 2.6 的接口补丁。**
- 【做法】新增管理端（可做成 `/admin` 独立布局）：
  - 数据看板（`GET /api/admin/stats` + ECharts：近 30 天发布趋势、分类占比、认领成功率、用户总数）；
  - 启事审核列表（`GET /api/admin/items?auditStatus=` + `POST /api/items/{id}/audit`）；
  - 下架/删除（offline/delete）、用户管理（`GET /api/admin/users` + status，封禁状态按 2.6 字段回显）；
  - 路由守卫加角色校验：`stores/user.js` 已有 `isAdmin` getter，路由加 `meta: { roles: ['admin'] }`，NavBar 对管理员显示"后台管理"入口。
- 【验收】管理员登录可见入口，审核/下架/封禁/看板全流程可演示；非管理员访问 /admin 被拒并跳转。

### 2.8 演示管理员账号无法登录（P0，v2.0 新增）
- 【现状】`DataInitializer` 给管理员 10000001 和全部演示用户的密码是 `UUID.randomUUID()`，没人知道，README 也写"口令随机仅展示"；任何"用演示管理员登录"的方案在现状下都做不到。
- 【做法】DataInitializer 给管理员固定口令（如 `admin123456`），普通演示用户统一口令（如 `123456`），启动日志打印账号密码；README 增加"演示账号"小节。
- 【验收】按 README 账号密码可直接登录管理员与演示用户，演示脚本不出现手工 SQL。

### ========== P1：小优化与安全项 ==========

### 2.9 管理员提权流程（P1）
- 【现状】提权靠手工 SQL（README 与 test_api.py 末尾均提示 `UPDATE user SET role=1`），演示易卡壳。
- 【做法】完成 2.8 后已基本解决（固定管理员可直接登录）；备选：注册时若账号在 `admin_whitelist` 配置名单中自动 role=1，或后台"用户管理"支持管理员互相提权。
- 【验收】演示脚本里不再出现手工 SQL。

### 2.10 前端 401 处理不闭环（P1，十行代码）
- 【现状】`api/index.js` 响应拦截器收到 401 清 localStorage，但不跳转，用户停在当前页看报错。
- 【做法】两处 clearSession() 后追加跳转逻辑（片段见附录 B）。
- 【验收】token 过期后任意操作 → 自动回登录页，登录后回原页。

### 2.11 后端零单元测试（P1，低成本加分）
- 【现状】pom 引入 spring-boot-starter-test 但 `src/test` 目录不存在。
- 【做法】补 JUnit 5 用例：`PHashUtil`（同图哈希一致、变体图距离 < 阈值、不同图距离 > 阈值）、`SearchService.similarityFromDist`（边界 0/64）、`AuthService`（重复学号注册、错误密码）。`mvn test` 进报告。
- 【验收】`mvn test` 全部通过，测试报告截图可入文档。

### 2.12 上传安全：仅校验扩展名（P1，报告"上线前必改"条目）
- 【现状】`FileStorageService.ALLOWED` 只查扩展名（gif/bmp/webp 均放行），文件内容不校验即落盘并被 `/uploads/**` 输出。
- 【做法】读文件头魔数校验（JPEG: FF D8 FF，PNG: 89 50 4E 47，GIF: GIF8，WEBP: RIFF....WEBP）；更彻底的方案：用 Hutool `ImgUtil` 二次编码后再落盘（顺带支持 2.13）。片段见附录 C。
- 【验收】改名为 .jpg 的文本文件被拒绝。

### 2.13 列表页直接用原图当封面（P1，体验/流量优化）
- 【现状】uploads 已 2.8M（仅演示数据）；卡片封面 4:3 约 300px 宽却加载原图。
- 【做法】落盘时同步生成缩略图（Hutool ImgUtil.scale，宽 480），`ItemVO` 增加 `thumbUrl`，`ItemCard`/列表用 thumbUrl、详情用原图；历史数据用 `reindex` 思路补一个 `POST /api/admin/regen-thumbs`。
- 【验收】列表页网络面板可见图片体积明显下降。

### 2.14 关键词检索：文档与实现不一致（P1）
- 【现状】schema.sql 建了 ngram 全文索引，但 `ItemService` 实际用 `like("title", k).or().like("description", k)`，全表扫、用不上该索引。
- 【做法】二选一：① 改 `MATCH(title,description) AGAINST(? IN BOOLEAN MODE)`（需手写 Mapper SQL，QueryWrapper 不支持全文语法）；② 保留 LIKE 并在 schema 与 06-数据库设计文档中删去全文索引或注明"数据量小，LIKE 足够"。**不要留着"文档说了但代码没做"的状态。**
- 【验收】实现与 06-数据库设计文档一致。

### 2.15 reindex 接口零鉴权（P1，v2.0 新增）
- 【现状】`SearchController.reindex()` 无任何鉴权，匿名用户可触发全表 pHash 重算，可被恶意调用消耗 CPU。
- 【做法】方法开头加 `UserContext.requireAdmin()`（与 AdminController 一致）。
- 【验收】匿名/普通用户调用返回 403。

### 2.16 删除启事不清理磁盘文件（P1，v2.0 新增）
- 【现状】`AdminService.deleteItem` 删除 item 与 item_image 记录，但 `uploads/` 下图片文件残留，长期积累孤儿文件。
- 【做法】删除记录前先收集图片 URL，复用 `FileStorageService.resolve()` 定位磁盘文件并 `Files.deleteIfExists`，删除失败仅记日志不阻断主流程。
- 【验收】删除启事后对应磁盘文件消失，数据库无残留记录。

### 2.17 前端无 404 兜底路由（P1，v2.0 新增）
- 【现状】路由表无 catchAll，乱输 URL 整页空白。
- 【做法】路由末尾加 `{ path: '/:pathMatch(.*)*', name: 'notFound', component: () => import('../views/NotFoundView.vue'), meta: { public: true, title: '页面走丢了' } }`，页面放"返回首页"按钮。
- 【验收】访问不存在的 URL 显示友好 404 页而非白屏。

### 2.18 移动端导航直接消失（P1，v2.0 新增）
- 【现状】`NavBar.vue` 在 ≤860px 时 `.nav-links { display:none }`，且没有汉堡菜单，手机上无法跳转失物墙/招领墙/以图搜图。
- 【做法】窄屏显示汉堡按钮，用 `el-drawer` 或折叠菜单承载导航链接（含消息铃铛与发布入口）。
- 【验收】浏览器 DevTools 切手机视口，所有页面可通过菜单导航。

### 2.19 发布启事图片非必填（P1，v2.0 新增）
- 【现状】发布接口 `files` 为可选，无图启事能发布成功，但永远无法进入以图搜图库，与项目核心卖点矛盾。
- 【做法】前端 PublishView 提交前校验至少 1 张图；后端 `ItemService.publish` 校验 files 为空（或全部不可读）时抛 `BusinessException("请至少上传一张物品图片")`。
- 【验收】无图发布前后端均被拦截并提示。

### 2.20 封禁实时性与异常信息脱敏（P1，v2.0 新增）
- 【现状】① 用户被封禁后，其已签发的 JWT 在 7 天有效期内仍可正常调用所有接口（仅登录时拦截）；② `GlobalExceptionHandler` 把 `e.getMessage()` 直接返回前端，500 时可能泄露 SQL/类名等内部信息。
- 【做法】① 演示规模下可在 `JwtInterceptor` 对携带 token 的请求查一次用户 `status`（数据量小、开销可忽略），status=0 则不写入 UserContext（等同匿名，受保护接口自然 401）；或在报告中说明"JWT 无状态、封禁最长 TTL 生效"的取舍。② 兜底异常统一返回"服务器繁忙，请稍后再试"，详细信息只 `log.error` 落日志。
- 【验收】封禁后该用户旧 token 立即失效（或报告写明取舍）；任意异常响应不出现 SQL/堆栈片段。

### ========== P2：体验与报告项 ==========

### 2.21 浏览量刷新自增无去重（P2，v2.0 新增）
- 【现状】`ItemService.detail` 每次请求 views+1，刷新页面即可刷量。
- 【做法】简单方案：内存 `ConcurrentHashMap` 记录 `itemId+IP/用户` 最近访问时间，30 分钟内重复访问不计数；或报告中注明"课程演示不做反作弊"。
- 【验收】同一访客短时间多次刷新只计一次（或文档注明取舍）。

### 2.22 以图搜图性能演进说明（P2，写报告即可，不必实现）
- 【现状】`BIT_COUNT(phash ^ q)` 全表扫，44 张毫秒级，万级也可接受。
- 【做法】报告性能章节写清当前复杂度与演进方案：64 位指纹分 4 段建前缀索引缩小候选集（参考 `Github/JImageHash`、`Github/314loveshiwu` 思路）、或迁移专门向量索引。当前规模不实现是合理取舍，写明即可。

### 2.23 CORS 与部署注意（P2）
- 【现状】`CorsConfig` 为 `allowedOriginPattern("*") + allowCredentials(true)` 全放行；前端走 Vite 代理实际不受影响。
- 【做法】保留（课内演示便利），在部署手册与报告"安全设计"一节写明：上线应收紧为具体域名、JWT secret 更换、数据库独立账号最小权限。

### 2.24 两套初始化数据路径并存（P2，v2.0 新增）
- 【现状】`data.sql`（mysqldump 导出）与 `DataInitializer`（读 manifest 播种）两套路径并存，README 虽写"二选一"，但新成员仍可能混淆，且两边账号密码策略不一致（配合 2.8 统一）。
- 【做法】部署手册定死推荐路径（建议：DataInitializer 为主，data.sql 仅作离线备份），统一两套路径的账号口令。
- 【验收】README/部署手册只有一条推荐初始化路径，账号密码一致。

### 2.25 数据库无物理外键（P2，v2.0 新增）
- 【现状】六张表只有索引没有 FOREIGN KEY，数据一致性全靠应用层。
- 【做法】在 06-数据库设计文档"设计取舍"小节写明"课程演示环境不建物理外键，一致性由 Service 层事务保证，便于删改演示数据"，避免答辩被追问。
- 【验收】文档有明确说明。
