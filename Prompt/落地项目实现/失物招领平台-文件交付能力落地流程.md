## 0. 先做选型决策（半天，全员对齐）

两个产品是两种路线，你们是 Web 平台课程设计，结论如下：

| 决策点 | 结论 | 理由 |
|---|---|---|
| 走 dsh 路线（Web 文件交付） | **采用** | 你们本来就是 Spring Boot + Vue，这条链路几乎原样搬得动 |
| 走 ZCode 路线（Electron 桌面 exe） | **不做**，只抄设计原则 | 5 人组 + 课程周期，维护 Electron 壳 + 自更新管道是负资产；小程序端已是你们的"桌面"形态 |
| 加 AI 能力 | 不加模型调用 | 准备清单已明确"AI 能力为零"，文件生成本身不需要 LLM——模板 + 数据填充即可 |
| 桌面化姿态 | 可选的"体验分"项 | 若答辩想展示"下载到桌面"的完整故事，做一个 10 行配置的 Electron 套壳（见第 5 节）即可，不碰自更新 |

**落地后你们平台多出的能力**（每个都对应 dsh 已验证的模式）：

1. 认领成功后自动生成**认领证明 PDF**，用户在消息中心点卡片下载/打印
2. 管理后台一键导出**统计报表 Excel**（发布量/认领量/分类分布）
3. 物品照片**打包 zip 下载**（找回物品的照片集）
4. 以图搜图结果生成**匹配报告 PDF**（绑定你们的核心亮点 M3，答辩素材直接多一页）

## 1. 总体架构：把 dsh 的三层解耦搬进 Spring Boot

dsh 的核心解耦是「**Agent 声明 → 持久事件 → UI 读事件渲染**」。你们平台没有 Agent，
但"生成文件的业务动作"和"前端展示"同样应该解耦——**业务代码只声明，UI 读表渲染**：

```
业务代码（认领成功/报表导出）
    │  调用 FileDeliveryService.deliver(type, path, title, bizRef)
    ▼
delivery 表（持久化交付事件：谁、什么文件、什么业务、状态）   ← 对应 dsh 的 deliverables/presented 事件
    ▼
前端消息中心/交付卡片（读 delivery 表渲染，不依赖生成方）      ← 对应 dsh 的交付卡片
    │
    ├── 预览：GET /api/file/download?id=…（受控下载）          ← 对应 dsh 的 /api/file
    └── 业务跳转：点击卡片跳到认领详情页                        ← 对应 dsh 的 present.open
```

三条铁律（全部来自 dsh 踩坑经验）：

1. **delivery 表只存服务端路径 + 元数据**，浏览器永远不传路径，只传 deliveryId
2. **所有文件路由在认证围栏之后**：JWT 过滤器先过，再进文件控制器
3. **业务方不直接操作文件响应**：生成文件 → 落盘 → 插 delivery 记录，就结束

## 2. 数据库设计（成员E，半天）

```sql
CREATE TABLE delivery (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id       BIGINT NOT NULL,                -- 接收人
  biz_type      VARCHAR(32) NOT NULL,           -- CLAIM_CERT / REPORT_EXCEL / PHOTO_ZIP / MATCH_REPORT
  biz_id        BIGINT,                         -- 关联业务：认领单id / 物品id
  title         VARCHAR(128) NOT NULL,          -- 卡片标题：'认领证明 #2026-0153'
  description   VARCHAR(255),                   -- 卡片副文案
  file_path     VARCHAR(512) NOT NULL,          -- 服务端相对路径（永远不下发原始绝对路径）
  file_name     VARCHAR(255) NOT NULL,          -- 下载时的展示文件名
  mime_type     VARCHAR(128) NOT NULL,
  file_size     BIGINT NOT NULL,
  status        TINYINT DEFAULT 1,              -- 1有效 0已失效（配合TTL清理）
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_user (user_id, created_at)
);
```

对应 dsh 的设计：`path` 存相对路径（服务端拼接根目录，等价于 dsh 的"绝对路径由服务端
从事件读回"）；`status` 支持过期下线（dsh 的 present.open 会对失效事件返回 404）。

## 3. 后端实现（成员C，2~3 天，核心）

### 3.1 统一交付服务 `FileDeliveryService`

```java
@Service
public class FileDeliveryService {
    private static final Path DELIVERY_ROOT = Paths.get(uploadRoot, "deliveries"); // 在白名单根下

    /** 业务方唯一入口：生成文件后调用。只声明，不掺和下载逻辑。 */
    public Delivery deliver(Long userId, String bizType, Long bizId,
                            String title, String description,
                            Path file, String displayName, String mimeType) throws IOException {
        // 校验：存在、是普通文件、resolve 后仍在 DELIVERY_ROOT 内（防符号链接/穿越，学 dsh present）
        Path normalized = file.toRealPath();
        if (!normalized.startsWith(DELIVERY_ROOT.toRealPath()))
            throw new IllegalArgumentException("file outside delivery root");
        // 落 delivery 记录，返回实体
    }
}
```

### 3.2 受控下载路由 `/api/file/download`（对应 dsh `serveFile`）

```
GET /api/file/download?id=<deliveryId>
```

逐条对照 dsh 的安全清单实现：

| dsh 的做法 | 你们的实现 |
|---|---|
| 只接受 sessionId/seq/index，路径服务端读回 | 只接受 deliveryId，路径从 delivery 表读回拼根目录 |
| 认证围栏在前（token→签名 cookie） | JWT 拦截器在前，校验 `delivery.user_id == 当前用户`（防越权下载别人的文件）|
| 必须普通文件、非符号链接 | `Files.isRegularFile` + `toRealPath()` 前缀校验 |
| 字节上限 413 | 文件生成时限定大小；响应设 `Content-Length` |
| `no-store / nosniff / CSP sandbox` | 同样三件套响应头 |
| MIME 白名单窄化 | 只允许 `application/pdf、xlsx、zip、png/jpeg`，其余拒绝（比 dsh 更严，你们场景固定）|
| 错误细分 | 404 不存在 / 403 越权或失效 / 413 超限 |

响应头关键行：

```java
response.setHeader("Content-Disposition",
    "attachment; filename*=UTF-8''" + URLEncoder.encode(fileName, StandardCharsets.UTF_8));
response.setHeader("X-Content-Type-Options", "nosniff");
response.setHeader("Cache-Control", "private, no-store");
```

### 3.3 三个生成器（纯 Java，无 AI 依赖）

| 生成器 | 技术 | 触发点 |
|---|---|---|
| 认领证明 PDF | OpenPDF（免费、无 AGPL 顾虑）或 iText 7 社区版 | 认领状态机走到"已认领"时生成，模板填字段：物品名/照片/双方信息/时间戳 |
| 统计报表 Excel | Apache POI（sxlsx 流式写） | 管理后台点"导出"，异步生成 + 卡片通知 |
| 照片打包 zip | `java.util.zip`（JDK 自带） | 物品详情页"打包下载全部照片" |
| 匹配报告 PDF（亮点绑定） | OpenPDF | 以图搜图完成后，把 Top-N 结果 + 汉明距离 + 缩略图写成报告 |

大文件走**异步**：`@Async` 生成 → 完成后写 delivery → 前端消息中心出卡片。
同步请求只负责"提交任务"，不阻塞等待——这是 dsh "present 是声明不是动作"的精髓。

## 4. 前端实现（成员D，1~2 天）

1. **交付卡片组件** `<DeliveryCard>`：读 delivery 记录渲染（标题/描述/文件类型图标/大小/时间），
   挂在消息中心和认领详情页。对应 dsh 的交付卡片——**从持久表渲染，刷新/重登都在**
2. **下载动作**：`<a :href="/api/file/download?id=xx">` 原生 a 标签下载即可（带 JWT 的场景用
   fetch → blob → `URL.createObjectURL` → a.download）
3. **生成中状态**：提交导出请求后卡片先显示"生成中…"，轮询或 WebSocket 收到 delivery 事件后
   变为可下载——对应 dsh 的"飞行超 250ms 才显示等待态"
4. **能力探测决定渲染**：管理后台没接 POI 前，导出按钮直接不渲染（对应 dsh 的
   "探测不到桌面就不给按钮"）

## 5. （可选加分项）10 分钟 Electron 套壳

如果答辩想展示"从官网下载 exe 装到桌面"的完整故事：

```
npm init -y && npm i electron electron-builder
```

```js
// main.js —— 全部就这些
const { app, BrowserWindow } = require('electron');
app.whenReady().then(() => {
  const win = new BrowserWindow({ width: 1280, height: 800 });
  win.loadURL('https://你们的服务器地址');   // 或开发时 http://localhost:5173
});
app.setAsDefaultProtocolClient('lostfound'); // 深链接，可选
```

```json
// package.json 的 build 段（electron-builder）
"build": {
  "appId": "com.course.lostfound",
  "win": { "target": "nsis" },
  "nsis": { "oneClick": false, "perMachine": false,
            "allowToChangeInstallationDirectory": true }
}
```

产出 `Setup.exe` 就是可分发安装包。**不做自更新**（课程项目不需要维护更新服务器）；
ZCode 那套 blockmap/差量更新留作答辩时"我们了解工业级方案"的口头加分即可。

## 7. 验收清单（对照两个产品的踩坑记录）

上线前逐项打勾：

- [ ] 修改 deliveryId 为别人的 id → 403（越权测试）
- [ ] 构造 `../` 路径或符号链接 → 403 且不泄露服务器路径
- [ ] 上传超限文件生成 → 413，前端有提示
- [ ] 下载 HTML 伪装成图片 → `nosniff` 生效，浏览器不执行
- [ ] PDF 文件名含中文/空格 → `filename*=UTF-8''` 编码正确
- [ ] 失效/删除的 delivery → 404，卡片同步消失或置灰
- [ ] 导出 10 万行 Excel → 异步不超时，卡片"生成中→可下载"流转正常
- [ ] 未登录直接访问下载 URL → 401 跳登录（认证围栏在前）
