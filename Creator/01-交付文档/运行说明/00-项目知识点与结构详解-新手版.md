# 一、五分钟认识这个项目

## 1.1 它解决什么问题

校园里丢东西 / 捡东西很常见。传统失物招领靠**文字描述**搜索（"黑色钱包"），但很多人**说不清也搜不准**。我们的创新点：**上传一张照片，系统靠"图片长相"自动匹配**全校的失物/招领启事——这就是「以图搜图」。

## 1.2 一句话技术栈

- **后端**：Java + Spring Boot 3.3（提供接口）+ MyBatis-Plus（操作数据库）+ MySQL（存数据）+ JJWT（登录令牌）+ **JImageHash（算图片指纹 pHash，核心算法）**。
- **前端**：Vue 3 + Vite（页面）+ Element Plus（UI 组件）+ Pinia（登录状态）+ axios（发请求）。
- **两者关系**：前端是"界面"，后端是"大脑+仓库"。前端通过 HTTP 接口（`/api/...`）问后端要数据；图片存在后端磁盘，数据库只存路径和一个 64 位"图片指纹"。

## 1.3 为什么"以图搜图"是亮点

市面同类项目几乎全是"文字搜索 + 增删改查"。我们用**感知哈希 pHash**：把每张图压缩成一个 64 位二进制指纹；两张图指纹**相差的位数（汉明距离）越小越像**。数据库里一条 SQL 就能算出"上传的图和库里哪张最像"，返回相似度百分比。这是纯 Java 实现、不依赖任何 AI 服务、可离线运行的真算法。

## 1.4 代码该怎么读（给小白的阅读顺序）

1. 先看**数据库表**（第五部分）——数据是根。
2. 再看**后端一个完整接口**（如注册）：Controller → Service → Mapper → 表。
3. 再看**前端一个页面**（如登录页）：页面 → api 封装 → 后端接口。
4. 最后啃**以图搜图**（第七部分）——全项目最值钱的部分。

## 1.5 运行形态：单 Web（2026-10-17 收敛）

答辩与交付统一用**浏览器**：后端跑起来后直接访问 `http://localhost:8080`，整套站点同源可用（后端托管 `frontend/dist`）。
登录态存 localStorage，图片走 `/uploads/**`，文件交付走 `/api/file/download`，没有任何客户端安装包。

> 历史：曾做过 Android APK（Capacitor）、iOS PWA、桌面 Electron 三端，代码层用 `IS_NATIVE/IS_DESKTOP` 分支适配。
> 因答辩不需要、且每次发版要重打包签名，2026-10-17 决定整体下线：客户端工程、依赖、端点与手册均移除/归档，

# 二、零基础概念补课

## 2.1 前后端分离

- **前端**：跑在浏览器里的界面（HTML/CSS/JS），负责"长什么样、点哪里"。
- **后端**：跑在服务器上的程序（这里是 Java），负责"算逻辑、存数据"。
- 两者**只通过 HTTP 接口通信**，互相不依赖对方代码。好处：可以并行开发、各自替换。

## 2.2 HTTP 与 REST API

- **HTTP**：浏览器和服务器说话的协议。一次"请求(request)"换一次"响应(response)"。
- **方法**：`GET`=取数据、`POST`=提交数据、`PUT`=改、`DELETE`=删。
- **REST**：一种接口设计风格——用"网址路径"表示资源、用"方法"表示动作。例：
  - `GET /api/items` = 取启事列表
  - `POST /api/items` = 新建启事
  - `POST /api/items/5/claim` = 对 5 号启事提交认领
- **状态码**：200 成功、401 未登录、403 没权限、404 不存在、500 服务器出错。

## 2.3 JSON

前后端传输数据的文本格式，长这样：

```json
{ "code": 200, "msg": "success", "data": { "id": 1, "title": "蓝色保温杯" } }
```

我们项目**所有接口**都返回这个三段式：`code`(状态)、`msg`(提示)、`data`(真正的数据)。前端拦截器会自动剥掉外壳只拿 `data`（见 8.5）。

## 2.4 框架 / 依赖 / 构建工具

- **框架**：别人写好的"半成品工具箱"，你按它的规矩组装自己的程序（Spring Boot、Vue 都是框架）。
- **依赖**：项目用到的别人写的库。Java 的依赖清单在 `pom.xml`，前端的在 `package.json`。
- **构建工具**：帮你"下载依赖 + 编译 + 打包"的程序。Java 用 **Maven**，前端用 **npm/Vite**。
- **Maven 仓库**：依赖的"应用商店"。我们配了阿里云镜像（下载快）。本地缓存目录 `C:\Users\emmmmm\.m2\repository`。

## 2.5 数据库与 SQL 基础

- **数据库(Database)**：存数据的仓库，本项目叫 `lost_found`。
- **表(Table)**：一张二维表，如 `user` 表、`item` 表。
- **行(Row)/记录**：表里一条数据。
- **列(Column)/字段**：表头，如 `account`、`title`。
- **SQL**：操作数据库的语言。`SELECT` 查、`INSERT` 增、`UPDATE` 改、`DELETE` 删。
- **主键(PK)**：唯一标识一行的列（`id`）。**索引(Index)**：给列建的"目录"，加速查询。

## 2.6 术语速查表

| 术语 | 通俗解释 |
|---|---|
| API / 接口 | 后端暴露给前端调用的"服务窗口"（一个网址+方法） |
| Endpoint | 某个具体接口的网址，如 `/api/auth/login` |
| Token / JWT | 登录后后端发的"门票"字符串，之后每次请求带上证明身份 |
| 哈希(Hash) | 把任意内容算成一串固定长度"指纹"的算法 |
| pHash | 感知哈希：图片的"视觉指纹"，相似的图指纹相近 |
| 汉明距离 | 两个等长二进制串**对应位不同的个数** |
| DCT | 离散余弦变换：把图像从"像素"转到"频率"的数学工具（pHash 用） |
| ORM / Mapper | 让 Java 对象和数据库表自动对应的技术/代码层 |
| Entity | 和数据库表一一对应的 Java 类 |
| DTO | 接收前端传参的 Java 类（入参） |
| VO | 返回给前端展示的 Java 类（出参） |
| 拦截器(Interceptor) | 请求到达业务代码前先经过的"关卡"（我们用它解析 token） |
| 中间件/插件 | 插入框架流程的组件 |
| 代理(Proxy) | 前端开发服务器把 `/api` 请求"转发"给后端，避免跨域 |
| 跨域(CORS) | 浏览器安全策略：默认禁止 A 网站脚本请求 B 网站；需后端放行 |
| BCrypt | 密码加密算法：单向、带盐，无法反推原文 |
| ThreadLocal | Java 里"每个线程私有的储物柜"，我们存当前登录用户 |
| 依赖注入(IoC/DI) | 对象由 Spring 创建并"塞"给你，不用自己 new |
| 注解(Annotation) | Java 里 `@xxx` 标记，给编译器/框架看的"标签" |
| HMR | Vite 热更新：改前端代码浏览器自动刷新，不用重启 |
| multipart | 一种 HTTP 请求体格式，用于上传文件（图片） |

## 3.3 它们如何协作（端口与代理）

```
浏览器 (你)
   │  打开 http://localhost:5173
   ▼
Vite 开发服务器 :5173   ←── 前端页面
   │  页面里发 /api/xxx、/uploads/xxx
   │  （Vite 代理转发，浏览器以为同源，无跨域）
   ▼
Spring Boot :8080      ←── 后端接口
   │  JDBC
   ▼
MySQL :3306 (lost_found)
   │
   └── 图片实际存在磁盘 backend/uploads/**，由后端映射成 /uploads/** 网址
```

- 后端**也**配了全局 CORS（`CorsConfig`），万一前端不走代理直连 8080 也能通。

### 各包职责与关键类

**common/**（通用件）
- `Result.java`：统一响应外壳 `{code,msg,data}`，静态方法 `Result.ok(data)` / `Result.fail(code,msg)`。
- `PageResult.java`：分页外壳 `{records,total,page,size}`。
- `BusinessException.java`：业务异常（带 code），抛出后被全局捕获转成失败响应。
- `GlobalExceptionHandler.java`：`@RestControllerAdvice` 全局兜底：业务异常原样透传、参数校验/请求体格式/媒体类型错误转友好 400、其余未知异常统一「服务器繁忙」**不把 Java 堆栈甩给前端**（防泄露内部信息）。

**config/**（配置）
- `CorsConfig.java`：全局跨域放行。
- `WebMvcConfig.java`：① 把磁盘 `uploads/` 映射成网址 `/uploads/**`；② 注册 JWT 拦截器到 `/api/**`（登录/注册除外）。
- `MybatisPlusConfig.java`：分页插件。
- `SecurityBeansConfig.java`：注册 BCrypt 编码器 Bean。
- `JwtProperties / FileProperties / ImageSearchProperties`：把 `application.yml` 里 `jwt.* / file.* / image-search.*` 读成 Java 对象（`@ConfigurationProperties`）。

**context/UserContext.java**：用 ThreadLocal 存"当前请求的登录用户 id 和角色"。提供 `requireUserId()`（没登录抛 401）、`requireAdmin()`（非管理员抛 403）。

**interceptor/JwtInterceptor.java**：每个 `/api` 请求先过这里——读 `Authorization: Bearer xxx`，校验并解析出 userId/role 放进 UserContext；请求结束清理。

**controller/**（接口入口，只做"收参→调 service→包 Result"）
- `AuthController`：`/api/auth/register|login|me`。
- `ItemController`：`/api/items`（列表/详情/我的/发布/标记找回）。
- `SearchController`：`/api/search/image|indexed-count|reindex`。
- `ClaimController`：认领申请/我的认领/收到的/审核。
- `UserController`：`/api/stats`、站内消息。
- `AdminController`：`/api/admin/*` 管理后台。

**service/**（业务逻辑，真正干活）
- `AuthService`：注册（查重+BCrypt 加密+建用户）、登录（校验+发 JWT）；**登录限流**（同一账号连错 5 次锁 10 分钟，防暴力破解）；「记住我」签发更长有效期 token（1440 分钟 / 30 天）。
- `ItemService`：发布（存图+算 pHash+入库，新启事**待审核**）、列表筛选分页（单页上限 100 防拖库）、详情（浏览量 30 分钟去重自增）、我的发布、entity→VO 转换、私信发送。
- `SearchService`：**以图搜图**（算查询图 pHash→调 mapper 汉明查询→组装相似度）、reindex 补算。
- `ClaimService`：认领申请/审核/**竞争状态机**（通过一条时自动关闭其余"审核中"申请；拒绝时仅当没有其他申请在审才回退物品状态）/发站内消息。
- `MessageService`：通知列表/未读数/已读（单条+全部）/详情。
- `AdminService`：用户封禁⇄解封/审核/下架/删除/重建缩略图/重算哈希，全部写 admin_log。
- `StatsService`：首页统计/后台看板（每日发布趋势、分类占比、用户数）。
- `FileStorageService`：图片落盘——**魔数（文件头）白名单校验**（jpg/png/gif/bmp/webp，仅看扩展名可被骗）→ 写 `uploads/yyyy/MM/uuid.jpg` → 同目录生成 **480px 宽缩略图** `_thumb`；启动/管理端可批量补生成（ensureThumbs）、删除用安全删除不抛异常。

**mapper/**（数据库操作）
- 八个 Mapper 都继承 `BaseMapper<T>`，自动获得单表增删改查（favorite / delivery 为 E-07、P1 新增）。
- `ItemImageMapper`：额外有 `searchByHash(q, threshold, limit)`——**以图搜图核心 SQL**（见 7.5）。
- `ItemMapper`：额外有分类统计、已找回计数、每日趋势。

**entity/**：`User/Item/ItemImage/ClaimRecord/Message/AdminLog/Favorite/Delivery`，与八张表一一对应（`@TableName` 指定表名，`@TableId` 指定主键自增）。

**dto/**（入参）：`RegisterReq/LoginReq/ItemForm/ClaimReq/ClaimAuditReq/ImageMatch/DmReq/ChangePasswordReq/UpdateProfileReq`。带 `@NotBlank/@Size/@Pattern` 校验注解。

**vo/**（出参）：`ItemVO`（含 `similarity`）、`UserVO`、`LoginVO`(token+user)、`ClaimVO`、`StatsVO`。

**util/**
- `JwtUtil`：签发/解析 JWT。
- `PHashUtil`：**哈希封装**——pHash（主用）+ aHash + dHash 三种算法可切换；`hash(bytes)` 返回 64 位 long；`hammingDistance(a,b)=Long.bitCount(a^b)`；`similarity(a,b)=(1-dist/64)*100`。

# 五、数据库设计详解

## 5.1 八表总览与关系

```
user ──1:N──> item ──1:N──> item_image(带 phash ★)
  │              │
  │              ├──1:N──> claim_record <──N:1── user(申请人)
  │              └──1:N──> delivery(交付文件：认领证明/报表/匹配报告)
  ├──1:N──> message
  ├──1:N──> admin_log
  └──1:N──> favorite(收藏, E-07)
```

- 一个**用户**可发布多条**启事**；一条**启事**可有多张**图片**；每张图片存一个 **pHash 指纹**。
- 一条**启事**可被多人**申请认领**（claim_record），申请人也是 user。
- **message** 是站内通知；**admin_log** 是管理员操作留痕。
- **delivery**（P1）记录"可下载的交付物"：归谁、什么类型（CLAIM_CERT / REPORT_CSV / MATCH_REPORT）、落盘相对路径、大小、状态；**行是唯一入口，文件只在受控接口后读取**（业务只声明，UI 按 id 取）。删启事时按 biz_id 级联删行+盘。
- **favorite**（E-07）是用户收藏，唯一键 (user_id, item_id)，重复收藏幂等。

## 5.2 逐表字段（精简版，全量见 06-数据库设计）

**user**：id / account(学号,唯一) / password(BCrypt) / nickname / avatar(emoji) / phone / role(0用户1管理员) / status(1正常0封禁) / create_time / update_time

**item**：id / type(lost寻物|found招领) / title / category / location / happen_time / description / status(业务状态) / cover_img(封面路径) / views / user_id(发布人) / audit_status(0待审1通过2驳回) / create_time / update_time

**item_image**：id / item_id / img_url / **phash(BIGINT,64位指纹)** / sort / create_time

**claim_record**：id / item_id / claimant_id(申请人) / proof(认领凭证) / contact / status(审核中|已通过|已拒绝) / reply / create_time / update_time

**message**：id / user_id(接收人) / type / title / content / ref_id / is_read / create_time

**admin_log**：id / admin_id / action / target_type / target_id / detail / create_time

**favorite**（E-07）：id / user_id / item_id / create_time，唯一键 `uk_user_item(user_id,item_id)`

**delivery**（P1）：id / owner_id(归属人) / biz_type(CLAIM_CERT|REPORT_CSV|MATCH_REPORT) / biz_id(关联启事/认领，报表可空) / file_name / file_path(相对 deliveries 根) / content_type / size / status / create_time

## 5.3 索引及为什么

- `item.idx_type_status(type,status)`：墙页按类型+状态过滤最快。
- `item.idx_category`、`idx_user`、`idx_create_time`：分类筛选、"我的发布"、按时间排序。
- `item_image.idx_phash(phash)`：以图搜图扫指纹列。
- `user.uk_account`：学号唯一，防重复注册。
- **为什么不建全文索引**：当前关键词搜索用 `LIKE` 在千级数据量下足够快；ngram 全文索引维护成本高、收益小，作为扩展项写进了 06-数据库设计的"索引取舍"一节（答辩可答"做过取舍"）。

## 5.4 物品状态机（M5 核心）

```
发布(lost)→ 寻找中      发布(found)→ 待认领
寻找中/待认领 ──有人申请认领──> 认领申请中
认领申请中 ──发布者通过──> 已找回(lost) / 已认领(found)
认领申请中 ──发布者拒绝──> 回退 寻找中/待认领
任意状态 ──管理员──> 已下架 / 已关闭
```

**为什么认领要发布者确认**：防冒领。申请人必须写"只有失主才知道的特征"(proof)，发布者核对后才通过。

## 5.5 为什么 pHash 存 BIGINT

64 位指纹正好装进一个 64 位整数（Java `long` / MySQL `BIGINT`，有符号）。存整数比存 64 个 0/1 或字符串**省空间、可比对**：MySQL 的按位异或 `^` 直接对两个 BIGINT 运算，`BIT_COUNT` 数出不同位数=汉明距离。

# 六、后端核心知识点

## 6.1 分层架构与数据流向

```
HTTP 请求
  → Controller（收参、校验、调 service、包 Result）
  → Service（业务逻辑、事务）
  → Mapper（SQL / ORM）
  → MySQL
返回时反向：entity → (service 转) VO → Result.data → JSON → 前端
```

**为什么分 entity/dto/vo 三种对象**：
- entity 贴着表，字段含 password 等敏感列，**不能直接返回前端**；
- dto 贴着"前端传什么"，带校验注解；
- vo 贴着"前端要什么"，只暴露安全字段（如把 user_id 换成 owner 昵称、加 similarity）。
分层隔离让改表不影响接口、改接口不影响表。

## 6.2 Spring Boot 常用注解速查

| 注解 | 作用 |
|---|---|
| `@SpringBootApplication` | 启动类标记（=配置+自动装配+扫描） |
| `@RestController` | 类里方法返回 JSON（=Controller+ResponseBody） |
| `@RequestMapping/@GetMapping/@PostMapping` | 映射网址+方法 |
| `@PathVariable` | 取路径参数 `/items/{id}` |
| `@RequestParam` | 取查询参数 `?type=lost` |
| `@RequestBody` | 取 JSON 请求体 |
| `@ModelAttribute` | 取表单字段（multipart 普通字段） |
| `@RequestPart` | 取 multipart 文件部分 |
| `@Service/@Component/@Configuration/@Bean` | 交给 Spring 管理/定义 Bean |
| `@Autowired` 或构造器注入 | 让 Spring 把依赖"塞"进来 |
| `@Transactional` | 方法内多条 SQL 要么全成功要么全回滚 |
| `@Valid` + `@NotBlank/@Size/@Pattern` | 参数校验 |
| `@RestControllerAdvice`+`@ExceptionHandler` | 全局异常处理 |
| `@ConfigurationProperties` | 把 yml 一段映射成对象 |

我们大量用 **Lombok `@Data`**（自动生成 getter/setter/toString）和 **`@RequiredArgsConstructor`**（自动生成构造器注入），所以看不到一堆样板代码。

## 6.3 统一响应与全局异常

- 所有接口返回 `Result`：成功 `Result.ok(data)`（code=200），失败 `Result.fail(code,msg)`。
- 业务里想报错就 `throw new BusinessException("xxx")`，`GlobalExceptionHandler` 捕获后转成 `Result.fail`，前端只看到友好提示。
- 参数校验失败（`@Valid` 不过）也被捕获，返回第一条校验消息。

## 6.4 JWT 登录态全链路（重点）

1. 登录成功 → `JwtUtil.generate(userId, account, role)` 用**密钥**签发一个 token（内含 sub=userId、role、过期时间）。
2. 前端把 token 存 `localStorage['shiguang_token']`。
3. 前端每次请求，axios 拦截器加头：`Authorization: Bearer <token>`。
4. 后端 `JwtInterceptor` 读头 → `JwtUtil.parse` 验签 → 解析出 userId/role → 放进 `UserContext`(ThreadLocal)。
5. Service/Controller 用 `UserContext.requireUserId()` 拿当前用户；没登录抛 401。
6. 请求结束 `afterCompletion` 清理 ThreadLocal（防线程复用串号）。

**为什么用 JWT 不用 Session**：无状态、服务端不存会话、天然支持分布式、前端只要保管字符串。

## 6.5 BCrypt 密码

- 注册：`passwordEncoder.encode(明文)` → 存密文（带随机盐，同密码每次结果不同）。
- 登录：`passwordEncoder.matches(明文, 密文)` 校验。**永远不存明文、也无法从密文反推**。

## 6.6 MyBatis-Plus 用法

- Mapper 继承 `BaseMapper<T>` 即得 `selectById/selectList/selectCount/selectPage/insert/updateById/delete...`。
- 条件用 `QueryWrapper`：`new QueryWrapper<User>().eq("account", x)`、`.like("title", k)`、`.orderByDesc("create_time")`、`.in(...)`、`.isNull(...)`。
- 分页：`selectPage(new Page<>(page,size), wrapper)`，需 `MybatisPlusConfig` 里注册分页插件。
- 列名 snake_case ↔ 字段 camelCase 自动映射（`map-underscore-to-camel-case: true`）。
- 复杂 SQL 用 `@Select` 注解直接写（如汉明距离查询、统计）。
- **防 SQL 注入**：MyBatis 的 `#{}` 是预编译参数，安全；切勿用 `${}` 拼用户输入。

## 6.7 文件上传与静态资源映射

- 前端 `FormData` 装图片 → `POST /api/items`（multipart）。
- 后端 `MultipartFile` 拿到 → `FileStorageService.store(bytes, name)`：校验**扩展名白名单 + 文件头魔数**（jpg/png/gif/bmp/webp；改后缀的假图片会被魔数识破）+ 大小(yml 限 5MB，前端上传前也拦一道) → 写 `uploads/yyyy/MM/uuid.jpg` → 再生成一张 **480px 宽缩略图**（列表页用小图省流量）→ 返回网址 `/uploads/yyyy/MM/uuid.jpg`。
- `WebMvcConfig.addResourceHandlers` 把磁盘 `uploads/` 映射成 `/uploads/**`，前端 `<img src="/uploads/...">` 直接显示。
- **坑（已修）**：不能先 `transferTo` 落盘再 `getBytes()` 算哈希——流被消费会失败。正确：`getBytes()` 读一次，既写盘又算哈希。

## 6.8 跨域 CORS 与代理

- 开发期前端走 Vite 代理（同源），无跨域。
- 后端另有 `CorsConfig` 全局放行，供直连场景。
- **原则**：跨域靠后端配置解决，不靠浏览器插件糊弄。

## 6.9 依赖注入与 Lombok

- 你不 `new Service()`，Spring 启动时创建好所有 `@Service/@Component/@Controller` 单例，通过构造器（`@RequiredArgsConstructor`）互相注入。好处：解耦、易测试、生命周期统一管理。

# 七、以图搜图算法详解（答辩重点）

## 7.1 什么是感知哈希

普通哈希（如 MD5）"差一个字节结果天差地别"，**不能**用于比相似。感知哈希(pHash)相反：**视觉相似的图，哈希相近**。它提取的是图像的"结构特征"而非字节。

## 7.2 pHash 计算五步（JImageHash PerceptiveHash）

```
原图
 ① 灰度化        → 去掉颜色干扰（颜色不该影响"是不是同一个东西"）
 ② 缩放到 32×32   → 去掉尺寸/分辨率差异，只留结构
 ③ DCT 离散余弦变换 → 从"像素域"转到"频率域"
 ④ 取左上 8×8 低频 → 低频=画面整体轮廓（最能代表"长相"），丢弃高频细节(噪点/纹理)
 ⑤ 按均值二值化    → 每个低频系数 > 均值记 1，否则记 0 → 得到 64 位指纹
```

最终一个 64 位二进制数（存成 BIGINT）。

## 7.3 汉明距离与相似度

- 汉明距离 = 两指纹**异或后 1 的个数** = 不同位的位数。Java：`Long.bitCount(a ^ b)`。
- 相似度 = `(1 - 距离/64) × 100%`。距离 0 → 100%；距离 10 → 约 84.4%。
- 判定相似：距离 ≤ 阈值（现行取 **12**，标定过程见 7.4 与 Creator/01-交付文档/11 §2.4）。

## 7.4 阈值怎么选

阈值是"像不像"的红线：太小→漏报（同一物品拍得稍不同就搜不到）；太大→误报（不相关的也匹配）。我们做了**真实验验**（`HashExperimentTest` + Creator/01-交付文档/11 报告）：把查询图做「轻变换」（裁剪 85%、亮度、对比度、灰度模糊、缩放 75%）和「强变换」（旋转 5°/10°、裁剪 70%、重度压缩等）两组，在含全部 6 种物品的检索库上测三种哈希在不同阈值下的查准率/查全率/F1。结论：**pHash 在阈值 10 时，非裁剪类轻变换召回 100%、无误检**；旋转和大裁剪是三种哈希共同的边界。阈值可在 `application.yml` 的 `image-search.hamming-threshold` 调整。

> **口径提示**：上面这段是"受控变体库"协议（6 对象/72 查询）下的结论，当时按 t=10 分析；
> **生产参数已在 2026-10-15 用端到端网格扫描重新标定为 `hamming-threshold=12`、`top-n=10`**
> （召回 85.7%、误检 0，见 Creator/01-交付文档/11 §2.4）。答辩报"12"并说明依据即可，不要报 10。

## 7.5 SQL 实现（★必背，含一个经典坑）

```sql
SELECT ii.item_id AS itemId, MIN(BIT_COUNT(ii.phash ^ #{q})) AS dist
FROM item_image ii
JOIN item i ON i.id = ii.item_id
WHERE ii.phash IS NOT NULL
  AND i.audit_status = 1                -- 只搜审核通过的
  AND i.status NOT IN ('已下架','已关闭')  -- 排除下架/关闭
GROUP BY ii.item_id
HAVING dist <= #{threshold}
ORDER BY dist ASC
LIMIT #{limit}
```

- `phash ^ #{q}`：**按位异或**，相同位得 0、不同位得 1。
- `BIT_COUNT(...)`：数 1 的个数 = 汉明距离。
- `GROUP BY item_id + MIN`：一条启事多图，取"最像的那张"的距离。
- `HAVING dist <= 阈值` 过滤，`ORDER BY dist` 最像的排前面，`LIMIT` 取 Top-N。
- **JOIN item 把审核/下架过滤"下推"进 SQL**：曾踩过"先 LIMIT 再在 Java 侧过滤"的坑——待审核项会占满 Top-N 名额导致漏结果（见 09-缺陷跟踪表），修复后过滤在 SQL 里先做、LIMIT 最后截断。

> **经典坑 1**：MySQL 里 `XOR` 是**逻辑**异或（真真得假，只返回 0/1），`^` 才是**按位**异或。误用 `XOR` 会让所有距离=0、相似度全 100%。我们踩过并修复，答辩被问"怎么算距离"务必答 `^` + `BIT_COUNT`。
> **经典坑 2**：过滤与 LIMIT 的顺序——必须在 SQL 内先过滤再 LIMIT，否则名额被不该出现的记录占掉。

## 7.6 pHash 鲁棒性 / 不鲁棒性

| 变换 | 鲁棒？ | 原因 |
|---|---|---|
| 缩放 | ✅ | 第②步统一缩到 32×32 |
| 亮度/对比度 | ✅ | 第⑤步按"均值"二值化，整体明暗抵消 |
| 压缩/轻微模糊 | ✅ | 低频结构不变 |
| 灰度化 | ✅ | 第①步本就灰度 |
| **旋转** | ❌ | DCT 对方向敏感，旋转会打乱低频布局 |
| 大幅裁剪/换背景 | ⚠️ 弱 | 结构变了 |

所以演示图变体**只用鲁棒的那些变换**，不用旋转（见 gen_seed_images.py 注释）。

## 7.7 性能与扩展性

- 当前规模（几十~几千图）：MySQL 全表扫 `BIT_COUNT` 足够快（实测 120 图索引：单次平均 **40ms**，20 并发总耗时 132ms——th=10/top-n=6 旧参数下测量；现行参数 th=12/top-n=10 下 41~54ms，见报告 11 §2.4）。
- 更大规模优化思路（答辩加分）：① 分段哈希+前缀索引粗筛；② 把 64 位拆 4 段建 BKD/倒排；③ 内存向量库。可引用"1000 张内全表扫够用，报告里写清权衡"。

## 7.8 与 aHash / dHash 对比

- **aHash**(均值哈希)：最简单，缩 8×8 按均值二值化。快但易受亮度/构图影响，准确率低。
- **dHash**(差值哈希)：比相邻像素梯度。比 aHash 稳，仍偏简单。
- **pHash**(DCT)：用频域低频，**抗压缩/亮度/缩放最好**，准确率最高，代价是多一次 DCT 计算。
- 我们选 pHash 因为它在"手机重拍"场景最稳。**准确率实验已完成**（`HashExperimentTest`，三算法 × 轻重两组变换 × 5 档阈值，P/R/F1 数据在 `scripts/exp_*.csv`，结论与图表见 Creator/01-交付文档/11 报告），答辩可直接引用数据。

# 八、前端核心知识点

## 8.1 Vue3 组合式 API 基础

- `ref(x)`：把基本类型变"响应式"，改 `.value` 界面自动更新；模板里直接用名字。
- `reactive(obj)`：对象版响应式。
- `computed(fn)`：派生值，依赖变化自动重算（如 typeText）。
- `watch(src, cb)`：监听变化触发副作用（如筛选条件变了重新请求）。
- `onMounted(fn)`：页面挂载后执行（通常在这里发第一次请求）。
- 模板指令：`v-if/v-else` 条件、`v-for` 循环、`v-model` 双向绑定、`@click` 事件、`:src/:to` 动态属性、`{{ }}` 插值。

## 8.2 SFC 三件套与 scoped

一个 `.vue` 文件 = `<script setup>`（逻辑）+ `<template>`（结构）+ `<style scoped>`（样式，只作用于本组件）。`<script setup>` 里定义的变量/函数模板可直接用。

## 8.3 路由与登录守卫（router/index.js）

- 路由表：网址 → 组件。`/`落地、`/auth`登录、`/home`、`/wall`、`/publish`、`/item/:id`、`/search-image`、`/profile`、`/admin/*`（后台）、`/:pathMatch(.*)*` 404 兜底。
- `meta.public`：标记公开页（落地/登录）；`meta.roles:['admin']`：标记管理员页。
- `beforeEach` 守卫：访问非公开页但没登录（localStorage 无 user）→ 跳 `/auth` 并记住来源；已登录访问 `/auth` → 跳 `/home`；**非管理员访问 /admin → 回 /home**。
- `afterEach`：按 meta.title 设置浏览器标题。

## 8.4 Pinia 登录态（stores/user.js）

- state：`token`、`info`（从 localStorage 恢复）。
- getters：`logged`、`isAdmin`。
- actions：`login/register`（调 api → 存 token+user）、`refresh`、`logout`（清 localStorage）。
- localStorage 键：`shiguang_token`、`shiguang_user`（路由守卫也读后者）。

## 8.5 axios 封装（api/index.js）

- `http = axios.create({baseURL:'/api', timeout})`。
- **请求拦截器**：有 token 就加 `Authorization: Bearer`。
- **响应拦截器**：后端返回 `{code,msg,data}`——code=200 直接返回 `data`（页面拿到的就是干净数据）；code=401 清登录态并跳 `/auth`（带回跳地址）；否则抛 Error(msg) 供页面 catch 提示。
- `api` 对象集中所有接口方法：register/login/me/stats/listItems/itemDetail/similar/myPublishes/publishItem/markFound/**dm**（私信）/searchByImage/indexedCount/applyClaim/myClaims/receivedClaims/auditClaim/messages/unread/**readAll/readOne**，以及管理端 **adminUsers/adminSetUserStatus/adminItems/adminAudit/adminOffline/adminDelete/adminStats/adminLogs/adminRegenThumbs/adminReindex**。页面只调 `api.xxx`，不写网址。

## 8.6 Element Plus 常用组件

`el-button`(按钮) `el-input`(输入) `el-select/el-option`(下拉) `el-date-picker`(日期) `el-form/el-form-item`(表单+校验) `el-upload`(上传) `el-tag`(标签) `el-tabs/el-tab-pane`(页签) `el-dialog`(弹窗) `el-empty`(空态) `el-checkbox` `el-badge`；消息 `ElMessage.success/error/warning`、确认框 `ElMessageBox`。

# 九、关键业务全流程走读

## 9.1 注册/登录

注册：前端提交 `{account,password,nickname}` → AuthController → AuthService 查重 → BCrypt 加密 → insert user → 发 JWT → 返回 `{token,user}` → 前端存 localStorage → 跳 /home。
登录：校验 `matches` → 发 JWT。错误密码返回 400「学号或密码错误」。

## 9.2 发布启事（含 pHash 入库）

前端 FormData（type/title/category/location/happenTime/description + files[]，图片必传至少一张）→ ItemController.publish（需登录）→ ItemService.publish：
1. insert item（status 按类型默认 寻找中/待认领，**audit_status=0 待审核**）。
2. 遍历每张图：`getBytes()` 读字节 → `FileStorageService.store` 落盘+缩略图 → `PHashUtil.hash(bytes)` 得 64 位 → insert item_image(url+phash)。
3. 第一张图设为 cover_img。
返回 ItemVO。发布后**需管理员审核通过**（audit_status=1）才在墙页可见、才参与以图搜图；发布者本人可在个人中心看到「待审核」标签。

## 9.3 以图搜图

前端上传 file → SearchController → SearchService.searchByImage：
1. `PHashUtil.hash(查询图字节)` = q。
2. `ItemImageMapper.searchByHash(q, 12, 10)`（阈值 12 / Top-10，见 `application.yml` 的 `image-search`，2026-10-15 网格标定）：SQL 算每条启事最小汉明距离，≤12 的按距离升序取 10。
3. 逐条转 ItemVO，`similarity=(1-dist/64)*100`。
4. 按相似度降序返回。前端渲染 Top-N 卡片+进度条+百分比+耗时。

## 9.4 认领与审核（含竞争状态机）

1. B 对 item 提交 claim（proof 认领凭证 + 联系方式）→ insert claim_record(审核中) + item.status=认领申请中 + 给发布者发 message。
2. 重复申请被拒（同 item 同申请人已有"审核中"）；**只有 寻找中/待认领 状态的物品才能申请**（白名单守卫）。
3. 发布者 A 在 Profile「收到的申请」看到（含 B 的学号/昵称/凭证/联系方式）→ audit(approve=true)：
   - 该 claim=已通过，item.status=已认领/已找回；**并为失主与认领人各生成一份「认领证明 PDF」写入 delivery 表**（失败只记日志、不影响审核事务）；
   - **自动关闭同 item 下其余"审核中"申请**（置已拒绝）并逐个通知申请人——两条申请不会同时"通过"。
4. 拒绝：claim=已拒绝；**仅当该 item 没有其他"审核中"申请时**才把 item 回退 寻找中/待认领（还有人在审就保持认领申请中）。
5. 非发布者审核 → 403。所有状态变化都发站内消息留痕。

## 9.5 管理后台

管理员（role=1）：进入 `/admin` 后台——**看板**（ECharts 每日发布趋势+分类环形图）、**启事审核**（待审/已通过/已驳回页签，通过/驳回/下架/删除）、**用户管理**（封禁⇄解封，封禁后该用户 token 实时失效）、**操作日志**、**运维工具**（重建缩略图/重算哈希/生成统计报表 CSV，报表也走 delivery 统一受控下载）。所有操作写 admin_log。非管理员访问后台 → 前端路由守卫回首页、后端接口 403（双层防护）。

## 10.3 常见错误速查

| 现象 | 原因/处理 |
|---|---|
| 启动报连不上数据库 | `backend/application-local.yml` 缺失或口令不对——该文件是本地必需（真实凭据只在里面，application.yml 只有占位符） |
| 端口 8080/5173 被占用 | 改 yml / vite.config 端口，或关掉占用进程 |
| MySQL 时区报错 | 连接串保留 `serverTimezone=Asia/Shanghai&useSSL=false` |
| 依赖下载慢/失败 | 确认 settings.xml 阿里云镜像；JImageHash 走中央仓库 |
| 搜图全 100% | 误用逻辑 `XOR`，应为按位 `^` |
| 搜图搜不到刚发布的 | ① 新发布需管理员审核通过后才可被搜到（SQL 已过滤待审）；② pHash 漏算可用 `POST /api/search/reindex` 补 |
| 页面白屏、只有背景色 | 生产构建报错（如 chunk 循环）导致 Vue 未挂载：F12 Console 看第一个红色报错；**dev 正常 ≠ build 正常**，改过打包配置后必须 build 后验证 |
| 图片 404 | 检查 `/uploads/**` 代理与 `file.upload-dir`；缩略图缺失可在后台「重建缩略图」 |
| 401 | token 过期/未带/账号被封禁；重新登录 |
| 前端改了不生效 | Vite 缓存，重启 `npm run dev` |

# 十一、答辩高频 Q&A

**Q1 以图搜图原理？** 答：pHash 感知哈希。灰度→缩 32×32→DCT→取 8×8 低频→按均值二值化得 64 位指纹；比对用汉明距离 `BIT_COUNT(a^b)`，≤阈值 12 判相似，相似度=(1-距离/64)×100，按距离升序取 Top-10。

**Q2 为什么 pHash 不是 aHash/dHash？** pHash 用频域低频，抗压缩/亮度/缩放最稳，适合手机重拍场景；aHash/dHash 更简单但准确率低。

**Q3 阈值 12 怎么来的？** 实验标定：写了 HashExperimentTest，对三算法在轻/重两组变换、5 档阈值下测 P/R/F1（数据在 scripts/exp_*.csv，报告 Creator/01-交付文档/11）；再用 `eval_recall.py --grid` 做端到端网格扫描——top-n=6 时召回只有 53.6%（被截断），改成 top-n=10/th=12 后召回 85.7% 且误检 0，同时 th=12 也是 mild 组 pHash 的 F1 峰值。阈值/TopN 都在 `application.yml` 的 `image-search` 里可配。

**Q4 旋转能搜到吗？** pHash 对旋转不鲁棒（DCT 方向敏感）。工程上可加旋转补偿（多角度哈希）或改用旋转不变哈希，这是可扩展点。

**Q5 图片存哪？为什么不全存数据库？** 存磁盘 `uploads/`，库只存路径+64 位哈希。避免 BLOB 撑爆库/仓库，备份和 CDN 都更灵活。

**Q6 搜索性能？** 千级图全表 `BIT_COUNT` 足够；更大可分段哈希前缀索引/倒排/向量库粗筛。

**Q7 为什么 JWT 不用 Session？** 无状态、服务端不存会话、易横向扩展、跨端友好。

**Q8 密码怎么存？** BCrypt 单向加盐哈希，只存密文，登录用 matches 校验。

**Q9 怎么防冒领？** 认领须填"只有失主知道的特征"，发布者人工审核通过才流转状态；全程站内消息留痕。

**Q10 怎么防 SQL 注入 / 上传漏洞？** MyBatis `#{}` 预编译；上传校验扩展名白名单 + **文件头魔数校验**（改后缀的假图片过不了）+ 大小限制 + UUID 重命名，路径规范化防穿越；真实口令只存 gitignored 的 application-local.yml，提交仓库里全是占位符。

**Q11 前后端怎么解决跨域？** 开发期 Vite 代理同源；后端 CorsConfig 全局放行兜底。

**Q12 事务用在哪？** 发布（item+多 image 一起成功/回滚）、认领审核（claim+item+message 一致）用 `@Transactional`。

**Q13 多人同时申请认领怎么办？** 竞争状态机：发布者通过 A 的申请时，自动把同 item 其余"审核中"申请置为拒绝并通知；拒绝某条时只有当没有其他在审申请才回退物品状态。不会出现"两个人都认领成功"。

**Q14 怎么防暴力破解密码？** 登录限流：同一账号连续错 5 次锁 10 分钟（内存计数）；密码 BCrypt 单向加盐；封禁用户的 token 实时失效（拦截器每次请求查库校验状态）。

**Q15 为什么要审核？审核前后的区别？** 内容治理：新发布 audit_status=0，墙页不显示、搜图 SQL 过滤掉（过滤下推进 SQL，先过滤再 LIMIT 防名额截断）；管理员通过后才可见可搜。驳回则只有发布者自己可见。

**Q16 为什么最后只保留 Web，不做 App？** 三端曾落地（Capacitor APK / PWA / Electron），但代价是每次改代码都要重打包、签名、分发，且真机环境（状态栏、WebView 缓存、明文 HTTP）反复出问题。课程验收看的是核心业务与算法，浏览器同源访问零安装、演示最稳，所以收敛为单 Web，把精力放回 pHash 与业务闭环。**这是主动取舍，不是做不出来**。

**Q17 交付文件（认领证明/报表）怎么做的？** 业务只往 `delivery` 表声明"要交付什么"，生成器（OpenPDF/CSV）落盘到受控目录，前端只拿 deliveryId；下载走 `/api/file/download`（no-store/nosniff/CSP + 文件名 UTF-8），浏览器内直接下载——渲染层全程不碰磁盘路径。

**Q18 踩过最深的坑？** 生产构建白屏：element-plus 按组件首字母拆成两个 chunk，组件间双向依赖跨 chunk 成环 → `Cannot access 'xx' before initialization` → Vue 没挂载，页面只剩背景色。**dev 正常不代表 build 正常**，现在改成单 chunk 并保留构建后冒烟。

# 十二、小白学习路线建议

1. **第 1 天**：跑通项目（第十部分），浏览器点一遍所有页面，F12 看 Network 里每个 `/api` 请求。
2. **第 2 天**：读第二部分概念 + 第六部分 6.1-6.3，理解分层和统一响应。
3. **第 3 天**：跟读"注册"和"发布"两条链路（Controller→Service→Mapper→表），在 IDEA 打断点单步。
4. **第 4 天**：啃第七部分 pHash，用 `scripts/` 里的图自己调 `/api/search/image` 看返回值。
5. **第 5 天**：读前端 8.1-8.5，改一个小界面（如加个字段）看热更新效果。
6. 之后：每人认领一个模块（M1-M6）能独立讲清+改 bug，即达到答辩要求。

> 记住分工纪律：AI/参考项目帮你"做出来"，但**每个知识点你必须能自己讲清楚**——答辩追问的就是这些。
