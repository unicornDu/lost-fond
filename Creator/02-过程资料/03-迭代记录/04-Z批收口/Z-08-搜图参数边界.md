# Z-08（P2·后端）`/api/search/image` 的 `threshold` / `topN` 无校验、无上限、匿名可传

> Z 批第 8 条（共 11 条）。执行前先读 `Deepseek_后端/00-索引与执行顺序.md`（JAVA_HOME 红线、验收命令）。总览与公共红线见 `00-索引与执行顺序.md` 及本文末尾。

## 现象与证据

调用链：

```java
// SearchController
public Result<List<ItemVO>> searchByImage(@RequestPart("file") MultipartFile file,
                                          @RequestParam(required = false) Integer threshold,
                                          @RequestParam(required = false) Integer topN) {
    return Result.ok(searchService.searchByImage(file, threshold, topN));
}
// SearchService
int th = threshold != null ? threshold : props.getHammingThreshold();
int tn = topN    != null ? topN    : props.getTopN();
return searchByHash(q, th, tn);         // → SQL: … HAVING dist <= #{threshold} LIMIT #{limit}
```

- **无 clamp、无下界上界、无需登录**；实测 `POST /api/search/image?topN=1000000` → `code=200`（本次因库内仅 120 行、命中仍 8 条而无影响，但表规模上来后就是廉价的资源消耗面）。
- 它还能在无任何身份的情况下改变检索语义（`threshold=64` 可让调用者拿到全部"可见"启事——不算数据泄露，但不是设计意图）。

## 根因

03 T-02 为了让 `eval_recall.py` 做网格扫描而加的覆盖参数，只考虑了"评测用"，没加边界；Creator/01-交付文档/04 也仅注明"评测覆盖用"。

## 修复要求

1. **加边界**（越界一律 clamp，不抛 400——避免评测脚本被边界值打断）：建议 `topN ∈ [1, 50]`、`threshold ∈ [0, 64]`（0/64 为位宽自然边界）。
   > ⚠️ **上界必须 ≥50**：`eval_recall.py` 的网格扫描用到 `topN ∈ {6, 10, 20, 50}`（见脚本 `for topn in (6, 10, 20, 50)`，L148），上界若设成 20 会直接打断网格复现。
2. **更好**：加开关 `image-search.allow-override`（local 默认 `true`，`application-prod.yml` 设 `false`），prod 下忽略入参、只用配置值，彻底避免生产被任意改变检索语义。
3. `Creator/01-交付文档/04` 的 `/api/search/image` 行补"参数越界处理策略"与"prod profile 下是否生效"。

## 验收标准

```bash
curl -s -o - -w "|HTTP %{http_code}" -X POST "http://localhost:8080/api/search/image?topN=1000000" -F file=@uploads/_query/q-cup.jpg
# → 返回条数 <= clamp 上界（当前应为 8），HTTP 200
curl -s -X POST "http://localhost:8080/api/search/image?threshold=-5" -F file=@uploads/_query/q-cup.jpg
# → 行为符合选定策略（clamp 到 0 → 空结果；或按你选定的语义）
python scripts/eval_recall.py --grid       # 网格仍能跑完（topN=50 不被拦）
```
