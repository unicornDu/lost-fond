# E-02（P1·后端+前端）管理员审核/下架结果通知发布者，驳回理由可选落库

> E 批第 2 条（共 8 条）。总览与公共红线见 `索引与执行顺序.md` 及本文末尾。
> ⚠️ 先读清楚：**认领申请（发布者审核申请人）那条链路已经闭环，不要动**。本条只补管理员对启事的审核/下架侧。

## 现象与证据

1. **管理员审核不通知发布者**：`AdminService.auditItem`（`AdminService.java:85-97`）只改 `audit_status` 并写 admin_log，**没有任何 messageMapper.push**；`offlineItem`（约 :99-110，含 Z-10 守卫）同样只改状态。发布者的启事被驳回/下架后**毫不知情**，启事在"我的发布"里只挂一个待审核/已驳回标记（且下架后连列表都看不见了）。
2. **驳回无理由**：`AdminController.audit`（`AdminController.java:51-53`）只收 `boolean approve`；驳回弹窗是纯确认框（前端 `AuditView.vue`，F-01 注释自述"理由落库涉及后端接口变更，留作后续增强"）。
3. **对照组（已闭环，作为实现模板）**：发布者审核认领申请时，`ClaimService.audit` 会把 `reply` 落库到 claim_record.reply、并 `push()` 站内消息给申请人，前端 `ProfileView.vue:143、162` 展示回复。本条要求管理侧达到同等闭环水平。

## 修复要求

1. **通知**：`auditItem` 与 `offlineItem` 操作成功后，向启事发布者（`it.getUserId()`）写站内消息，复用 `ClaimService.push` 的消息模型口径：
   - `type="audit"`、`refId=itemId`（与 message 表 `ref_id` 注释"关联业务ID（item/claim）"一致）；
   - 标题/文案区分四种情形：审核通过 / 审核驳回 / 违规下架 / 下架后重新通过（若 AuditView 的"重新通过"走 auditItem approve=true，自然覆盖）；
   - content 带 `it.getTitle()`，与 ClaimService 通知写法对齐。
2. **驳回理由（可选透出）**：`AdminController.audit` 增加可选参数 `@RequestParam(required = false) String reason`（≤200 字，超长 400）：
   - 驳回（approve=false）时 reason 拼入通知 content（如"驳回理由：xxx"，无 reason 用默认文案"内容不符合发布规范"）；
   - 通过时忽略 reason；
   - `admin_log` 的 detail 追加 reason 摘要（保持 log 表列宽内，先核对列宽）。
3. **前端**：`AuditView.vue` 驳回改为弹窗输入理由（ElMessageBox.prompt，可留空）；下架同理。移除"F-01 留作后续增强"注释。
4. **幂等基线（红线 4，本条必踩）**：审核通知是新增 message 写入。`test_api.py` 中涉及 admin audit/offline 的用例会使 message 不再回基线——按 00 索引红线 4 二选一：把新增通知计入新基线（数字更新并在 99-修复记录注明"因 E-02 审核通知新增 N 条"）或断言后清理。**禁止删断言。**
5. **单测 + 回归**：
   - `AdminServiceTest` 补：auditItem 驳回 → verify 向发布者写 1 条 type=audit 消息；offlineItem 同理；审核已团聚启事仍走 B-03 守卫 400 且不写消息。
   - `test_api.py` 补：驳回带 reason 后，查询发布者消息列表断言 content 含 reason。
6. **文档同步**：`Creator/01-交付文档/04` 的 audit/offline 端点补 reason 参数与通知行为；`Creator/01-交付文档/01` FR6.1 补"审核/下架结果站内通知发布者"；`Creator/01-交付文档/02` 若有管理端时序图补消息分支。
